# 배송 예측 정보 - 서빙 API 스펙 (Phase 2, 통합플랫폼 협의용)

## 요약 (3줄)

- 상품코드 하나만 넘기면 "N일 이내 도착확률"을 돌려주는 로직을 만들었고, 2026년 상반기
  실제 주문 44.7만 건으로 재검증해서 정확하다는 것까지 확인했습니다(오차 0.1~1.4%p).
- 조회는 룩업테이블 방식이라 계산이 사실상 즉시입니다(실측 0.45ms/건, 아래 3번 참고).
- 지금 필요한 건 이 로직을 통합플랫폼 상품 페이지에 연결하는 방법 협의입니다(아래 5번).

`serve.py`의 `DeliveryPredictor.predict()`가 이 스펙대로 이미 동작하는 참조 구현입니다.
조회 기준은 상품코드입니다(네이버 상품페이지 방식처럼 SKU 단위 도착확률이 원래 요구사항).

## 1. 요청 (통합플랫폼 -> 예측 서비스)

```json
{
  "product_code": "10641055",
  "order_date": "2026-07-02",
  "standard_delivery_date": "2026-07-12"
}
```

- `product_code` (권장): 상품코드. 이것만 있으면 나머지는 서버가 `product_lookup.csv`로
  자동 조회합니다.
- `order_date` (필수): 주문일 (오늘 날짜로 고정해도 됨)
- `vendor_name`/`category_top`/`category_mid` (선택): 상품코드를 못 주는 경우의 대체
  입력, 또는 product_lookup 조회 결과를 명시적으로 덮어쓰고 싶을 때 사용.
- `standard_delivery_date`(=`표준납기일`, 선택, **2026-07-13 추가**): 통합플랫폼이 이미
  보유·표시 중인 그 값. 협력사 이력이 아예 없는 신규/콜드스타트 상품에서 `cat`/`global`
  대신 이 값 기반의 더 정확한 레벨(`sla_bucket`)로 응답합니다 - 같은 주문
  검증에서 콜드스타트 구간 오차가 절반 이하로 줄어듦(아래 6번 한계표, known_risks.md
  참고). 협력사 이력이 있는 상품(전체의 95%+)은 이 값과 무관하게 sku/vendor_mid/vendor로
  응답하므로 영향 없습니다.
  **안 넘기면(2026-07-27 변경)**: 서버가 `product_lookup.csv`/`vendor_sla_lookup.csv`에
  저장된 상품코드·협력사 과거 최빈값으로 자동 추정해서 채웁니다 - 연동 초기라
  통합플랫폼이 이 값을 아직 못 넘기는 상황에서도 `sla_bucket`까지 활용할 수 있게 하기
  위함입니다. 이 경우 응답의 `sla_estimated`가 `true`로 표시됩니다. **실제 값을 이미
  갖고 계시면 그걸 넘기시는 게 항상 더 정확합니다** - 추정치는 어디까지나 과거 이력
  기반 근사값입니다.

## 2. 응답 (예측 서비스 -> 통합플랫폼)

```json
{
  "level": "sku",
  "resolved_vendor": "주식회사 원창유통",
  "resolved_category": "탕비용품/식품 > 생활용품",
  "product_name": "인쇄명함",
  "product_recognized": true,
  "sample_size": 2451,
  "median_days": 3.0,
  "sla_estimated": false,
  "표준납기일_사용값": null,
  "holiday_adjusted": false,
  "confidence_level": "high",
  "headline": {"day": 7, "date": "2026-07-09", "weekday": "목", "prob": 0.93, "threshold": 0.9, "threshold_met": true, "reliable": true},
  "by_day": [
    {"day": 1, "date": "2026-07-03", "weekday": "금", "prob": 0.02, "reliable": true},
    {"day": 2, "date": "2026-07-04", "weekday": "토", "prob": 0.31, "reliable": true},
    {"day": 3, "date": "2026-07-05", "weekday": "일", "prob": 0.52, "reliable": true},
    {"day": 5, "date": "2026-07-07", "weekday": "화", "prob": 0.79, "reliable": true},
    {"day": 7, "date": "2026-07-09", "weekday": "목", "prob": 0.93, "reliable": true},
    {"day": 10, "date": "2026-07-12", "weekday": "일", "prob": 0.97, "reliable": true},
    {"day": 14, "date": "2026-07-16", "weekday": "목", "prob": 0.99, "reliable": true},
    {"day": 21, "date": "2026-07-23", "weekday": "목", "prob": 0.998, "reliable": true},
    {"day": 30, "date": "2026-08-01", "weekday": "토", "prob": 0.999, "reliable": true}
  ]
}
```

- `sla_estimated`/`표준납기일_사용값`(2026-07-27 추가): 요청에 `standard_delivery_date`를
  안 넘겼는데 서버가 자동 추정했으면 `sla_estimated=true`이고, `표준납기일_사용값`에 그
  추정 날짜가 담깁니다. 요청에 실제 값을 넘겼거나(그 값이 그대로 `표준납기일_사용값`에
  담김) 추정도 불가능했으면(`level`이 `sku`/`vendor_mid`/`vendor`처럼 협력사 이력만으로
  이미 결정된 경우 등) `sla_estimated=false`입니다 - 이 필드는 "결과가 추정치 영향을
  받았다"가 아니라 "이 날짜 값 자체가 추정치인가"만 알려줍니다(예: `level`이 `sku`면
  표준납기일과 무관하게 결정되므로, `sla_estimated=true`가 떠도 결과 자체엔 영향 없음).
  화면에 실제 날짜를 노출할 계획이면 `sla_estimated=true`일 때만 "추정치" 문구를 붙이는
  걸 권장합니다.

- `confidence_level`("high"/"medium"/"low")과 `by_day[].reliable`/`headline.reliable`
  (2026-07-07 추가): 2026H1 홀드아웃으로 레벨×day마크별 캘리브레이션을 전 구간(1~30일)
  검증한 결과, 레벨마다 오차가 10%p를 넘는("재검토 필요", 이 프로젝트가 이미 쓰는 기준)
  구간의 **위치가 서로 다릅니다** - `cat`/`global`은 중간 구간(2~10일)만 나쁘고 21일
  이후 회복됩니다. (`vendor_mid`는 원래 21/30일이 11.6%p/10.7%p로 불안정했으나
  2026-07-10 해당 레벨만 학습 기간을 2018~2025로 넓혀 7.0%p/7.8%p로 개선, 지금은 전 구간
  안정 - known_risks.md 참고.) 그래서 "reliable_from_day" 같은 단일 값 하나로는 표현이 안 되고, 레벨별로
  구체적인 불안정 day 집합(`serve.py`의 `LEVEL_UNRELIABLE_DAYS`)을 두고 `by_day`/`headline`
  각 항목에 `reliable` 플래그를 붙였습니다. `confidence_level`은 레벨 전체를 요약한
  값이고, 실제 판단 근거는 `reliable` 플래그입니다. **이 값을 화면에서 숨길지/흐리게
  표시할지/문구로 대체할지는 UI 정책이라 서버는 판단하지 않습니다** - 아래 5번 참고.

- `product_recognized`(2026-07-07 추가): `product_code`를 줬는데 `product_lookup.csv`에도
  없고 `vendor`/`category_top`/`category_mid`도 안 준 경우 `false`. "신규라 자기 데이터가
  없는 상품"과 "애초에 존재하지 않는 코드(오타 등)"를 구분할 방법이 없어서(품목 마스터가
  아니라 주문 이력 기반), 이 경우 `global` 평균을 자신 있게 보여주는 대신 이 플래그로
  알립니다. **`false`면 확률을 그대로 노출하기보다 "상품코드를 확인해 주세요" 같은
  안내로 대체하는 걸 권장합니다** - GUI(`gui_predict.py`)에 이미 이렇게 반영돼 있습니다.
  단, 이것도 완전한 판별은 아닙니다 - 진짜 신상품이라 아직 주문이 0건인 경우도 똑같이
  `false`가 뜹니다(구분할 근거 자체가 없음).

- `level`: 몇 단계 세밀한 정보로 답했는지, 세밀한 순서대로
  `sku`(상품코드 자체 데이터) > `vendor_mid`(협력사+상품중분류)
  > `vendor`(협력사 전체) > `cat`(대분류 전체) > `global`(전체 평균).
  (2026-07-08: 원래 있던 `vendor_cat`(협력사+대분류) 레벨은 제거함 - 같은 주문 집합에
  vendor_cat과 vendor를 동시 적용해 비교한 결과, 세분화가 오히려 정확도를 떨어뜨렸음
  (예: 5일 지점 vendor_cat 4.7%p 오차 vs vendor 1.1%p). known_risks.md 참고.)
  **`sku`로 답하는 비율은 물량이 많은 히트상품(명함, 복사용지, 종이컵 등 소모품)에 한정됩니다**
  - 대부분의 상품코드는 개별 주문 이력이 워낙 적어서(중앙값 2건/반년) 자기 데이터로
  예측할 수 없고, 자동으로 `vendor_mid` 이상으로 폴백됩니다. 이건 의도된 동작입니다
  (표본이 부족한데 억지로 SKU 단위로 예측하면 신뢰할 수 없는 숫자가 나옵니다).
- `resolved_vendor`/`resolved_category`/`product_name`: 상품코드로 자동 조회된 협력사/
  카테고리/상품명 (참고·디버깅용, product_lookup.csv에 없는 신규 상품이면 비어있음)
- `holiday_adjusted`: 주문일이 공휴일 연휴 시작 1~3일 전이라 확률이 하향 보정됐는지.
  보정 적용 구간은 연휴 길이별로 다름(2026-07-08 확인) - 신정/광복절 같은 **하루짜리
  공휴일**은 day1/2/3/5/7/10까지 보정하고, 2일 이상 연휴는 day1/2/3/5까지만 보정함
  (day7 이후는 이 경우 보정 시 오히려 오차가 커진다는 게 검증됨) - `08_holiday_adjustment.py`의
  `ADJUSTABLE_DAYS_BY_BUCKET` 참고
- `headline`: 확률이 90%(기본값, `headline_threshold`로 조정 가능)를 처음 넘는 날짜. **화면
  첫 줄에 보여줄 값은 이걸 쓰세요** - 고정된 날짜(예: 3일)의 확률을 그대로 보여주면 배송이
  느린 상품은 낮은 숫자(18.5% 등)가 나와 "상품에 문제 있나?"로 오해받기 쉽습니다. `threshold_met`
  이 `false`면 day30까지도 90%를 못 넘겼다는 뜻(배송이 불안정한 상품 신호 - 예: 향수 사례는
  30일에도 84.6%에 그침).
- `by_day[].prob`: "주문일로부터 day일 이내 도착할 누적 확률" (0~1) - 펼쳐보기 등 상세 화면용

## 3. 성능 특성 (실측치, 2026-07-06)

| 항목 | 실측값 | 비고 |
|---|---|---|
| 초기화(룩업테이블 로딩) | 232ms | 서버 기동 시 1회만 발생 |
| 단건 조회 | 0.45ms/건 | 100건 반복 평균, 룩업테이블 방식이라 계산량이 거의 없음 |
| 세그먼트 테이블 크기 | `segment_distributions.csv` 562KB | 메모리에 통째로 올려도 부담 없음 |

이 수치는 지금 구조(파케이/CSV 룩업 + 순수 파이썬)를 그대로 API 서버 프로세스 하나에
얹었을 때 기준입니다. 실제 배포 아키텍처(사이드카/별도 서비스/온프레미스 등)에 따라
네트워크 왕복 시간이 추가되므로, 최종 응답시간은 배포 방식이 정해진 뒤 재측정 필요.

## 4. UI 표시 방식 (제안)

**하이브리드 방식을 제안합니다**: 화면 첫 줄엔 응답의 `headline` 필드를 그대로 크게
보여주고(네이버 스타일, 예: "7/9(목) 도착확률 94%"), 펼쳐보기에 `by_day` 전체를 보여주는
방식입니다.

이유: 상품마다 확률이 올라가는 속도가 다릅니다. 감열지처럼 빠른 상품(1일 79.5%, 2일
91.1%)은 한 줄 요약으로 충분하지만, 통신설치자재처럼 느린 상품(7일 56.6%)은 90%를
넘는 날짜가 훨씬 뒤라 **고정된 날짜(예: 3일)의 확률을 그대로 보여주면 낮은 숫자만 보여서
"상품에 문제 있나?"로 오해받습니다** - 그래서 `headline`이 고정된 날짜가 아니라 "확신할 수
있는 날짜"를 상품마다 다르게 찾아줍니다. 펼쳐보기에서는 날짜별로 서서히 올라가는 모습을
보여주면 느린 상품도 오히려 신뢰를 줄 수 있습니다.
`headline_threshold`(기본 90%)나 표시 방식은 UI 쪽 튜닝 사항이고 API 재설계 없이
조정 가능합니다.

## 5. 통합플랫폼팀과 확인이 필요한 부분

1. **상품코드 마스터 연동**: `product_lookup.csv`(상품코드->협력사/카테고리/상품명 매핑)를
   우리 쪽에서 학습 데이터로 만들어 제공하거나, 통합플랫폼의 실시간 상품 마스터를 그대로
   조회하는 방식 중 무엇으로 할지 협의 필요. 신상품(학습 데이터에 없는 상품코드)은
   `resolved_vendor`가 비어있으므로, 이 경우 통합플랫폼이 자체 상품 마스터에서 협력사/
   카테고리를 채워서 다시 요청하는 폴백 경로가 필요합니다.
2. **신규 협력사/신규 상품(콜드스타트) 처리**: 학습 데이터에 없는 상품/협력사는
   **(2026-07-13 개선)** `standard_delivery_date`를 같이 넘기면 `cat`/`global`(전체
   평균) 대신 표준납기일 기반 레벨(`sla_bucket`)로 응답합니다 - 협력사
   이력이 없어도 "이 상품이 원래 며칠짜리 납기인지"는 항상 아는 정보라는 점을 활용한
   것으로, 같은 주문 검증에서 콜드스타트 구간 오차가 절반 이하로 줄었습니다(예: day7
   14.8%p -> 7.7%p). `standard_delivery_date`를 안 넘기면 기존처럼 `cat`/`global`로
   응답합니다(하위 호환). (**2026-07-14**: 당초 `cat_sla`/`sla_bucket` 2단 구조였으나,
   같은 주문 검증에서 `cat_sla`가 커버리지 이득 없이 평균 오차만 더 나빠 제거하고
   `sla_bucket` 단독으로 단순화 - known_risks.md 참고. `sla_bucket`은 전 구간 10%p
   이내로 안정적입니다(같은 날 vendor 경계선 세그먼트 반영 이후 최대오차 8.6%p->9.7%p로
   소폭 상승 - 여전히 기준 이내지만 known_risks.md에 부수효과로 기록해둠).)
   그래도 `cat`/`global` 레벨은 여전히 "항상 부정확"은 아니지만 특정 구간에서
   `reliable=false`가 뜰 수 있습니다(2026-07-07 검증 - 중간 구간만 나쁘고 21일
   이후는 오히려 정확한 패턴). 이 구간을 화면에서 어떻게 다룰지는 아래 옵션 중 선택
   가능합니다: ① `confidence_level`이 낮은 상품은 확률 전체 숨김 ② `reliable=false`
   구간만 숨기고 나머지(장기 확률 등)는 그대로 표시 ③ 단기는 "산정 중" 문구로 대체하고
   장기(21일+)는 정상 표시. 서버는 `confidence_level`/`by_day[].reliable`로 근거만
   제공합니다. **어느 옵션으로 갈지(특히 "예측을 숨길지 말지")는 고객에게 무엇을
   약속하느냐의 서비스 정책 결정이라 김정훈 본부장 결정 사안**이고, 결정된 방향의 구체적
   구현 방식(문구/디자인/적용 위치)을 통합플랫폼과 협의하는 순서를 제안합니다.
3. **재학습/갱신 주기**: 지금은 2023~2025 데이터로 학습해서 고정된 세그먼트 테이블을
   씁니다. 이 파일을 얼마나 자주 갱신할지(월 1회/분기 1회) 정책 필요. 갱신 시
   `05_growth_vendor_flag.py`로 급성장 협력사가 생겼는지 먼저 확인 권장(과거 이 문제로
   캘리브레이션이 12.7%p까지 틀어진 적 있음).
4. **API 호출 방식**: 배치(주문 목록 화면에 여러 건 한 번에) vs 단건(상품 상세 페이지 진입 시
   1건) 중 어느 쪽이 필요한지에 따라 `predict()`를 배치 처리하도록 벡터화할 수 있습니다
   (현재는 단건 호출 기준으로 구현).
5. **(2026-07-08 해결)** ~~공휴일 캘린더 최신화~~: `08_holiday_adjustment.py`가 이제
   `holidays` 파이썬 라이브러리로 공휴일 목록을 매 실행마다 자동 생성합니다(음력 공휴일
   정확한 날짜, 임시공휴일/선거일 포함, 연도별 법 개정도 반영 - 2026년 제헌절 재지정
   사례로 검증). 수동 갱신 불필요해졌습니다 - known_risks.md의 "HOLIDAYS 리스트를
   수동 관리 -> holidays 라이브러리로 전면 교체" 항목 참고.
6. **주문 시각(시:분) 데이터 존재 여부**: 지금 확보한 원본 데이터(109개 컬럼)에는
   `주문일자`가 날짜만 있고(`YYYYMMDD`), 시:분 정보가 전혀 없습니다. 그래서 네이버의
   "15:00까지 결제 시 오늘 발송" 같은 마감시간 구분을 지금 모델은 반영하지 못합니다
   (오전 주문과 밤 11시 주문을 동일하게 취급). 통합플랫폼의 실제 주문 시스템 로그에는
   시각까지 기록되고 있는지 확인 필요 - 있으면 마감시간 피처를 추가 검증할 수 있고,
   없으면 이 오차는 현재 구조상 감수해야 합니다.
7. **배포 아키텍처**: 온프레미스/클라우드/기존 서비스에 라이브러리로 얹는 방식 중 무엇으로
   할지는 전적으로 통합플랫폼팀 인프라 정책에 달려있어 이쪽에서 제안할 수 없는 영역 -
   협의에서 결정 필요.
8. **(참고, 지금 당장 결정 불필요) `headline` "미달" 상품 표시**: 일부 상품(예: 발주->출하가
   유독 길고 특정 달에만 몰려 주문되는 배치성 발주 패턴 상품 - 원인은 정기 대량발주 등으로
   추정되나 원산지 데이터가 없어 수입 여부는 확정할 수 없음)은 `threshold_met=false`로
   응답합니다. 이런 상품에 "다음 입고 예정"
   같은 별도 문구가 필요할지는 재고연동(Phase 3, 임영빈 팀장 알파 인터페이스류) 논의와
   같이 볼 사안 - `phase3_backlog.md` 참고.
9. **표준납기일(SLA)과 모델 예측이 다른 경우 표시 정책**: 상품의 72.3%는 모델 예측이
   표준납기일과 같거나 더 빠르지만(오히려 SLA가 보수적), 7.0%(물량 5.1%)는 모델이 5일
   초과로 더 늦게 예측합니다 - 이 그룹의 95.1%는 이미 Kraljic 분류상 전략재/병목재(배치성
   발주 등 공급위험 高 상품군)와 겹칩니다. 저희 쪽 판단으로는 ① 모델 예측을 SLA에 맞춰

   범위 밖(구매팀/계약 부서 협의 필요)이라 판단했습니다. 그래서 화면에서 gap 크기에 따라
   차등 표시(경미하면 그대로, 크면 표준납기일과 모델예측을 나란히 보여주며 안내 문구 추가)
   하는 방식을 제안드립니다 - UI 정책 협의가 필요합니다. 근거자료는
   `sla_gap_analysis.csv`/`sla_gap_report.txt`, known_risks.md의 "표준납기일(SLA) vs

## 7. 예상 질문 (FAQ)

**Q. 새 상품이 추가되면 어떻게 되나요?**
A. `product_lookup.csv`에 없는 상품코드는 협력사/카테고리 입력이 있으면 `vendor_mid` 이상
레벨로, 없으면 `global`(전체 평균)로 자동 대체됩니다. 별도 조치 없이 안전하게 동작하지만
정확도는 낮습니다(위 6번 콜드스타트 참고).

**Q. 모델이 틀리면 어떻게 알 수 있나요?**
A. 지금은 수동으로 `03_distribution_fit.py`를 재실행해 홀드아웃 캘리브레이션을 재확인하는
방식입니다. 정기 자동 모니터링 체계는 아직 없음(Phase 3 이후 검토 항목).

**Q. 화면에 뭐라고 표시하나요?**
A. 하이브리드 방식을 제안합니다(위 4번). 최종 문구/디자인은 UI 담당과 별도 논의가
필요합니다.

**Q. 우리 시스템에서 얼마나 자주 호출해야 하나요?**
A. 상품 페이지 조회 시마다 1회 호출하는 걸 기본으로 가정했습니다. 세그먼트 테이블이
자주 안 바뀌므로(재학습 주기 = 월/분기 단위) 캐싱도 가능합니다.
