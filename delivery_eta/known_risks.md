## vendor_mid day21/30 오차의 정체 - 모델 결함 아닌 "협력사×카테고리×월 단발 이상치" (2026-07-14)

### 배경
vendor_mid의 21/30일 잔존 오차(7.0/7.8%p - 2018 확장으로 10%p 아래로 내려온 후에도
남아있던 것)의 개선 방안을 찾기 위해 원인부터 분해함.

### 실측 (2026H1 홀드아웃, vendor_mid 응답 37,641건)
- 방향: day21/30 모두 **과대예측**(모델이 실제보다 빨리 도착한다고 봄) - pred 93.0/97.1%
  vs actual 86.0/89.3%.
- 쏠림: 세그먼트별 오차기여도(gap×n)를 계산하면 **상위 10개 세그먼트가 전체 기여도의
  92.8%** (주문 수로는 24.5%). 1위 케이눅/생활용품·기타 하나가 압도적.
- 시간 패턴: 상위 기여 세그먼트들을 월별로 분해하면 전부 "**한 달만 극단적으로 느리고
  나머지 달은 정상**" 시그니처:
```
케이눅/생활용품·기타:      4월만 mean_lt 48일(21일내 0%), 훈련기간(24~25년)엔 100% 정상
현웅디자인/KT그룹 일체복:  4월만 30.5일(21일내 3.1%), 2/5/6월은 2~9일 정상
예일토탈싸인/출판·인쇄:    5월만 42.8일(21일내 3.2%), 1~4/6월은 5~11일 정상
현웅디자인/생활용품:       3월만 31.3일, 나머지 달 정상
```
- 케이눅은 협력사 전체가 아니라 "생활용품/기타" 카테고리만 망가짐(같은 기간 접속자재 등
  나머지 6개 중분류는 94.8~100% 정상) - 협력사 전면 이상이 아닌 특정 상품군 이슈.
- growth_vendor_flags.txt(물량 급증 감시)에는 안 걸림 - 물량 폭증형이 아니라 순수
  "그 달만 유독 늦어진" 케이스라 기존 감시망 사각지대.

### 결론
학습기간 확장·세분화·바이어스 보정 같은 **모델 측 개선으로는 못 고치는 유형** - 훈련
데이터는 이 조합들이 원래 빨랐음을 정확히 반영하고 있고, 문제는 2026년 특정 월의
실물(공급/물류/기록) 이슈. 단발 이상치라 다음 재학습 주기(해당 월이 train으로 편입되고
holdout이 갱신되면)에 자연 희석될 가능성이 높음.

### 추가 확인 (2026-07-15) - 착시 아님, 원인 위치는 "발주->출하" 단계
"내부 기록 지연 착시(외부사 21일 리드타임 사례와 같은 유형) 아니냐"는 가설을 배송완료일자/
입고일자/발주일자/출하일자 4개 날짜를 전부 대조해서 확인함(상위 기여 세그먼트 4개, 이상
발생 월만):
```
케이눅/생활용품·기타(4월,n=2331):        배송완료lt=48.4  출하lt=47.3  발주lt=0.0
현웅디자인/KT그룹 일체복(4월,n=1755):     배송완료lt=30.5  출하lt=29.4  발주lt=1.4
예일토탈싸인/출판·인쇄(5월,n=340):        배송완료lt=42.8  출하lt=42.0  발주lt=0.0
```
- **발주는 거의 즉시**(0~1.4일) - 주문 접수/발주 처리 단계는 정상.
- **배송완료lt와 출하lt가 거의 동일**(예: 48.4 vs 47.3) - 즉 지연의 거의 전부가
  "발주 이후 실제 출고되기까지"(출하 준비 단계)에서 발생하고, **출하 이후 배송완료까지는
  약 1일로 정상**. 라스트마일 배송 자체는 문제없음.
- 입고일자는 이 진단에 쓸 수 없음(원래부터 배송완료일자보다 구조적으로 늦게 찍히는 필드
  - EDA에서 이미 확인된 사실이라 비교 기준이 안 됨).
- **결론: 착시 아님, 실제 지연.** 다만 문제 위치가 "배송(라스트마일)"이 아니라 "발주 후
  출하 준비"(조달/재고/포장 등) 단계로 특정됨 - 과거 영풍기획 배치수입 패턴과 같은 계열의
  이슈. 조기경보 기능을 만들 경우 "전체 lt 이상"이 아니라 "발주->출하 소요일 이상"을
  직접 감시하는 게 더 정확한 신호가 됨.

## sla_bucket day5/7 오차의 주범은 "6일 표준납기" 그룹 - 관찰 기록만, 조치 없음 (2026-07-14)

### 배경
"5일/7일을 별 의미 없이 기재하는 담당자가 많아 sla_bucket의 day5/7 오차가 큰 것 아니냐"는
가설을 실측 검증. 라운드넘버 쏠림 자체는 사실(표준납기 7일 186,177건, 5일 59,825건 vs
6일 15,276건)이나, 오차 원인으로는 반증됨.

### 실측 ('4~7일' 버킷 내부를 정확값별로 분해, 2026H1 홀드아웃)
```
표준납기=4일 (n=973):     day5 gap= 2.0%p  day7 gap=1.4%p
표준납기=5일 (n=59,825):  day5 gap= 5.4%p  day7 gap=1.3%p
표준납기=6일 (n=15,276):  day5 gap=10.6%p  day7 gap=5.8%p  <- 주범
표준납기=7일 (n=186,177): day5 gap= 1.6%p  day7 gap=0.9%p  <- 최다 물량이 가장 정확
```
라운드넘버(5/7일)는 오히려 정확하고, 소수파인 6일 그룹만 실제 배송이 버킷 평균보다
유독 느림(실측 73.6% vs 예측 84.3%, day5 기준). sla_gap_report.txt의 "5일 초과 불일치
122개(전략재+병목재 95.1%)" 사례 중 종이컵(동방제지, SLA=6일, 모델=13일)이 이 패턴의
실물 예 - 6일 그룹과 SLA-gap 상품군이 겹칠 가능성 있음(미검증).

### 결론 - 조치 없음
sla_bucket 자체가 롤백 기준(10%p) 이내라 지금 손볼 사안 아님. 나중에 sla_bucket을
재검토하게 되면(예: vendor 확장으로 population이 더 얇아져 10%p를 넘게 되면) "6일
그룹만 별도 버킷으로 분리" 또는 "6일 그룹의 협력사/카테고리 구성 확인"부터 시작할 것.

### 후속 검증 (2026-07-16) - 구성 확인 + 분리안 테스트, 분리 기각
위에 남겨둔 두 시작점을 실제로 실행함:
- **구성**: sla_bucket 응답 주문 중 6일 표준납기는 284건뿐. 협력사 쏠림 약함(상위 3개
  20.8%), 대분류는 청소/생활/의료·안전/소방·사무/전산 3종에 64.8% - 특정 집단의 문제가
  아니라 일반 MRO 카테고리에 분산.
- **sla_gap(122개 SKU)과 겹침: 0개** - "종이컵(동방제지, SLA=6일)이 이 패턴의 실물 예"
  라던 이전 추정은 반증됨. 종이컵류는 sku 레벨에서 응답되므로 sla_bucket 모집단에 아예
  없음 - 모집단 혼동이었음. (교훈: 전체 표준납기=6일 주문 15,276건 기준의 관찰과, 실제
  sla_bucket으로 서빙되는 6일 주문 284건은 다른 모집단 - 서빙 관점에서는 후자만 중요.)
- **분리안(4~7일 버킷을 4·6일/5일/7일로 쪼갬) same-order 테스트: 기각.** 9개 구간
  오차 합계 39.4p(현행 통합) vs 40.2p(분리) - day1/2가 크게 악화되고 나머지는 근소
  개선에 그침. 심지어 분리하면 "5일 그룹 day5=10.6%p", "7일 그룹 day7=10.2%p"로 10%p
  초과 구간이 새로 생김(현행 최대 9.7%p). "세분화가 항상 좋은 게 아니다"의 **다섯 번째**
  확인 사례(vendor_cat, 관리회계, 카테고리 카스케이드, cat_sla에 이어).
- 결론: 현행 5구간 유지 확정, 이 관찰 항목 종결.

### 추가 시도 (2026-07-16) - 카테고리 분리도 착시로 판명, 여섯 번째 반증
사용자가 "5%p 넘는 구간이 여전히 아쉽다"고 지적, "정확한 날짜"가 아니라 "대분류"로
4~7일 버킷을 쪼개면 개선되는지 재시도함(6일 그룹의 대분류가 청소/안전/사무에 몰려
있었던 것에서 착안).
- **집계만 보면 대성공처럼 보임**: 9구간 합계 39.4p(현행) -> 22.3p(카테고리 분리).
- **개별로 뜯어보면 반대**: 이건 서로 다른 카테고리의 오차가 반대 방향으로 상쇄된
  "다른 모집단 착시"(vendor_cat/카테고리 카스케이드/cat_sla와 동일 함정) - 실제로
  안전/소방용품(n=1,052, 무시 못 할 물량)에 이 방식을 적용하면 자체 오차가 **16.2%p로
  악화**(현행 9.19%p보다 나쁨) - 롤백 기준(단일 레벨 10%p 초과) 위반. 탕비용품/식품

- **"믿을 만한 카테고리만 vetting" 안 검토했으나 시도 안 함**: 바로 앞선 공휴일 보정

## 상품코드 중 낙찰 협력사 변경 - 구조 변경 불필요 확인 (2026-07-27, AI혁신팀 질의)

### 배경
AI혁신팀 회의에서 나온 질문: "주문 도중 낙찰 협력사가 바뀌면, 상품코드(sku) 단위 예측 대신
협력사 단위 예측으로 바꿔야 하지 않느냐". 협력사가 바뀌면 배송 특성이 달라질 수 있으니
일리 있는 지적이라 실측 검증함.

### 검증
- **이미 흔한 현상**: sku 레벨로 예측하는 2,171개 상품 중 370개(17%)가 2023~2026년
  (lookup_source 기간) 사이 협력사 2곳 이상이었음(`product_lookup.csv`의
  `n_협력사_고유값` 컬럼에 이미 기록돼 있었음 - 그동안 참고용으로만 방치).
- **2026H1 홀드아웃 same-population 비교**(단일 협력사 SKU n=173,120 vs 협력사
  2곳 이상 SKU n=52,668, 전 구간 1~30일):
```
        1일    2일    3일    5일    7일   10일   14일   21일   30일
단일    1.0p   1.9p   3.5p   3.4p   2.1p   0.6p   0.6p   0.9p   0.3p
멀티    0.3p   2.5p   3.0p   0.5p   1.2p   1.2p   0.1p   0.1p   0.0p
```
**멀티벤더 SKU가 오히려 여러 구간(1·3·5·7·14·21·30일)에서 더 정확** - 협력사가
바뀌었다고 sku 레벨 예측이 나빠지는 현상이 관측되지 않음.

### 결론 - 반영 안 함(구조 변경 근거 없음)
- sku 레벨은 이미 vendor 레벨보다 정확(홀드아웃 비중 52.7% vs 34.7%+8.4%) - 멀티벤더
  여부와 무관하게 상품코드 기준 유지가 최선.
- 짐작되는 이유: sku 레벨은 물량 많은 히트상품에만 적용(`SKU_MIN_N=200`)되는데, 이런
  상품은 ①복수 협력사 병행 소싱이 흔하거나 ②KT 내부 처리 프로세스/상품 특성이 배송
  속도를 협력사 정체성보다 더 좌우할 가능성.
- **다만 감시 여지는 있음**: 이번 검증은 "3~4년 누적 이력"이라 "협력사 전환 직후 한두
  달"처럼 짧은 과도기의 일시적 저하는 못 잡음. 필요 시 growth_vendor_flags.txt/
  procurement_delay_flags.txt와 같은 패턴으로 "이 상품코드의 최근 1개월 주력
  협력사가 과거 이력과 다르다" 월간 자동 플래그 추가 검토 가능(미구현, 요청 시 진행).

## cat_sla 제거 - sla_bucket 단독으로 단순화 (2026-07-14)

### 배경
"cat_sla와 sla_bucket 순서가 맞나, 30일 비교도 해보라"는 질문에서 시작. 아래 항목의
사후 집계표(다른 모집단끼리 비교)만 보면 sla_bucket이 8/9 구간 압승처럼 보였으나, 이건
vendor_cat/카테고리 세분화 때와 같은 "다른 모집단 비교" 착시일 수 있어 같은 주문
counterfactual로 재검증함.

```

2일      9.61p      4.54p    sla_bucket
3일     11.64p      7.53p    sla_bucket

### 결론 - 반영 완료
`cat_sla`를 LEVELS에서 제거, `sla_bucket` 단독으로 단순화. 재학습 결과:

확인 사례(vendor_cat 제거, 관리회계 재분류 기각, 카테고리 세분화 기각에 이어).

### 참고: 같은 날 vendor_mid vs vendor도 재검증(학습기간 확장 반영 후)
vendor_mid가 같은 주문(37,641건, 95.9% 매칭) 기준 **9구간 전부 vendor보다 우세**
(예: day7 vendor_mid 0.24p vs vendor 5.97p) - cat_sla와 달리 모호함 없음. 현재 폴백

## spot(일회성) 발주 배제 - vendor 레벨 학습에 반영 완료 (2026-07-13, 본부장 지시 사항 검증)

### 배경
본부장 지시 "spot(일회성) 발주 건은 배제하고 평균을 계산하는 전처리가 필요하지 않을까".
"spot"을 "그 협력사 안에서 이 상품코드가 아주 드물게 등장(협력사x상품코드 조합 train
건수 <5)"로 정의해서 검증.

### 시행착오 1 - 설계 의도 오해
처음엔 "spot 주문도 잘 맞혀야 한다"고 전제하고, spot을 vendor에서 뺀 뒤 그 주문들을
① vendor 건너뛰고 cat_sla~global로 폴백 ② 그 협력사의 spot 주문만 모은 별도 평균
("vendor_spot") 두 가지로 대체 서빙하는 걸 검증함 - 둘 다 실패(①은 전 구간 악화,
②는 표본이 잡탕이라 들쭉날쭉). 이 결과로 "구현해도 순이득 없음"이라고 잘못 결론
내렸었음.

**사용자 정정**: "spot 주문은 굳이 예측이 필요한 주문이 아니다" - 즉 spot 자체의
정확도는 애초에 신경 쓸 대상이 아니고, **학습(평균 계산)에서만 제외하고 서빙 시에는
spot/non-spot 구분 없이 정제된 vendor 평균을 그대로 반환**하면 되는 설계였음. 별도
폴백 로직이 필요 없어서 처음 판단("복잡도 대비 실익 낮음")도 틀렸던 것 - 실제로는
구현이 아주 단순함(학습 데이터만 필터링).

### 검증(같은 주문 기준, non-spot vs 기존)
- **vendor**: non-spot 전 구간에서 일관되게 개선(day3 1.27->0.97p, day5 1.43->1.05p,
  day7 1.20->0.87p, day10 0.80->0.60p, day14 0.50->0.39p, day21 0.40->0.34p).
- **vendor_mid**: 같은 방식으로 검증했더니 오히려 악화되는 구간이 더 많음(day1~7
  대부분 악화, day10/14/21/30만 미세 개선) - 이미 협력사x중분류로 좁혀진 그룹이라
  spot까지 더 빼면 표본이 과도하게 얇아짐. **vendor에만 적용, vendor_mid는 그대로.**

### 실제 반영 후 재검증(production 모델, 2026H1 홀드아웃)
```
vendor 레벨 전체(spot 31.3% 포함) 표준 캘리브레이션 리포트상 오차는 소폭 상승한 것처럼
보임(예: day5 0.7%p->1.2%p) - 이건 spot의 부정확함이 그대로 드러난 것이라 의도된
결과(spot 정확도는 목표가 아님). 진짜 확인 대상인 non-spot만 다시 뽑으면:
day3 1.27->0.97p, day5 1.43->1.05p, day7 1.20->0.87p, day10 0.80->0.60p,
day14 0.50->0.39p, day21 0.40->0.34p, day30 0.10->0.09p (9개 구간 중 7개 개선)
```
전체/다른 레벨 영향 없음, 롤백 기준(전체 3%p 악화, 특정 레벨 10%p 폭발) 미해당.

### 구현
`03_distribution_fit.py`에 `VENDOR_SPOT_THRESHOLD=5` 추가, `main()`에서 vendor 테이블만
협력사x상품코드 조합 train 건수 5 미만인 주문을 제외하고 재계산. 서빙 로직(`serve.py`)은
변경 없음 - spot/non-spot을 구분하지 않고 그대로 vendor 조회.

### 주의사항(향후 재학습 시)
`phase1_report.txt`의 "vendor 레벨별 캘리브레이션" 숫자가 이전보다 약간 나빠 보이는 게
정상임(spot 포함 전체 평균이라서) - "vendor 나빠졌나?"하고 재작업하지 말 것. 실제
개선 여부를 확인하려면 non-spot만 따로 걸러서 봐야 함.

### 다른 레벨 확장 검토 - 전부 기각 (2026-07-13)
"vendor 말고 다른 레벨에도 spot 제외를 적용하면 개선되는가" 확인. 같은 spot 기준
(협력사x상품코드 조합 train<5)으로 sku/cat_sla/sla_bucket/cat/global 전부 검증:
```
sku:        효과 없음(9개 구간 전부 동일) - sku는 이미 최소 200건 기준이 spot 기준(5건)
            보다 훨씬 높아 구조적으로 spot이 이 레벨에 거의 안 들어옴(spot 비중 0.7%)
cat_sla:    전 구간 악화(spot 비중 40.9%)
sla_bucket: 3개 악화, 6개 동일, 개선 0개(spot 비중 46.6%)
cat/global: 홀드아웃 응답 0건(이미 표준납기 버킷이 다 흡수, 검증 불가)
```
cat_sla/sla_bucket은 애초에 협력사 이력이 얕은 콜드스타트성 주문 비중이 높아서(spot
비중 40%+), vendor처럼 "자주 파는 것과 가끔 파는 것을 나눌" 만큼 표본이 풍부하지 않음
- 빼면 정보만 사라지고 노이즈 감소 효과가 없음. **vendor 레벨에만 적용한 현재 구현이
맞고, 추가 확장 불필요.**

## 레벨×day마크 바이어스 보정 - 검증 완료, 구현 보류 (2026-07-13, 본부장 지시 사항 검증)

분할(2023~2024 학습 -> 2025로 편차 측정, 홀드아웃 누수 방지)로 레벨x day마크별 평균
편차(바이어스)를 구해 2026H1 홀드아웃에 적용.

### 결과 요약

- **vendor_mid 14~30일**: 유일하게 실질적 여지 확인(14일 2.9->1.2p, 21일 7.0->5.8p,
  30일 7.8->6.7p, 다른 구간은 이미 양호해 영향 적음).
- **전 레벨 일괄 적용 시 부작용**: 레벨별 오차는 개선돼도 **전체 캘리브레이션은 악화**
  (day7 0.07->1.07p) - 현재 낮은 전체 오차가 레벨 간 편차의 우연한 상쇄에 부분적으로
  기대고 있어서, 한쪽만 고치면 상쇄가 깨짐. 선별 적용만 가능, 일괄 적용 불가.

### 결론
**구현 보류.** vendor_mid 14~30일 구간(1~1.7%p 개선)이 유일하게 남은 여지인데, 같은
날 이미 이 레벨을 2018~2025로 확장해서 해당 구간을 11%p대 -> 7%p대로 낮춰둔 상태라
추가 개선폭이 작음. 별도 보정계수 저장/서빙 시 클리핑 레이어를 새로 만드는 복잡도
대비 실익이 낮다고 판단 - 오늘 이미 레벨 2개(cat_sla/sla_bucket)를 추가한 상태라
파이프라인 복잡도 누적을 피함. 본부장 보고 시: "검증 완료, 유일한 개선 여지(vendor_mid
장기구간)는 같은 날 다른 방식(학습기간 확장)으로 이미 해소되어 별도 구현은 보류"로 설명 가능.

## 표준납기 버킷 레벨(cat_sla/sla_bucket) - 콜드스타트 개선 반영 완료 (2026-07-13)

### 배경
콜드스타트(cat/global, 4.5%) 오차를 줄일 새 레벨 검토. 협력사 이력이 없는 신규 상품도
표준납기일은 주문 시점에 항상 알 수 있고, 전체 주문의 92%가 표준납기일 이내 도착하는
등 예측력 있는 신호. 순수 카테고리 세분화(중분류/소분류/세분류)와는 성격이 다름 -
카테고리를 더 쪼갠 게 아니라 협력사가 선언한 별도 정보를 추가한 것.

### 설계
표준납기일을 5개 버킷(~3일/4~7일/8~14일/15~30일/31일~)으로 나누고, vendor 다음, cat
이전에 2단계 폴백 삽입: 대분류x납기버킷(cat_sla) -> 납기버킷 단독(sla_bucket) -> 대분류
(cat) -> 전체(global). 표준납기일 미입력 시 두 신규 레벨을 건너뛰고 곧장 cat/global로
폴백 - 기존 클라이언트 하위 호환.

### 검증(같은 콜드스타트 주문 21,087건, 2단조합 vs 기존)
전 구간 오차 합계 62.7%p -> 29.5%p로 절반 이하 축소. 악화는 21일 하나뿐(절대값 작음).

### 재학습 결과(2026H1 홀드아웃)
표준납기일이 있는 홀드아웃 주문은 cat/global이 사실상 0건 - 전부 신규 레벨로 흡수됨.
cat_sla는 3/5/7/10일 구간이 여전히 10%p 초과(cat과 같은 패턴, 폭은 줄어듦) -
LEVEL_UNRELIABLE_DAYS 등록, confidence "low". sla_bucket은 전 구간 10%p 이내 -
unreliable 없음, confidence "medium". 전체 day-mark 오차 0.0~1.5%p로 기존과 동급,
다른 레벨 영향 없음.

### 구현
03_distribution_fit.py에 SLA_BUCKET_BINS/LABELS, 납기버킷 컬럼(표준납기일 없으면 NaN,
groupby/merge에서 자동 제외돼 하위 호환), LEVELS에 cat_sla/sla_bucket 추가. serve.py의
predict()에 표준납기일(선택) 파라미터, _sla_bucket_of()/_lookup() 반영. API_SPEC.md에
standard_delivery_date(선택) 필드 추가.

### 의사결정 주체(2026-07-13 확인)
"콜드스타트 예측을 숨길지 말지"(API_SPEC.md UI 옵션)는 서비스 정책이라 본부장 결정
사안이고 이 레벨 추가와는 무관 - 정책이 뭐든 정확도를 개선하는 내부 로직 변경이라
vendor_mid 확장과 같은 성격으로 바로 반영함.

## 카테고리 세분화(중분류/소분류/세분류) 검증 - 순이득 없음, 반영 안 함 (2026-07-13, 본부장 지시 사항 검증)

### 배경
본부장 검토 미팅에서 "대분류만 쓰지 말고 중분류/소분류/세분류를 활용한 세그먼트로
분석해봐라, 단계가 늘어도 정확도를 올리는 게 중요하다"는 지시. 서비스카테고리 필드가
실제로 4단계 전부 채워져 있음을 확인(예: "생활용품/기타 > 생활용품 > 화장지류 > 물티슈")
- 현재는 앞 2단계(대분류/중분류)만 사용 중이었음.

### 검증 방법과 흔한 함정 회피
1차 시도에서 "세분화 조합이 매칭 안 되면 실패" 방식으로 비교했더니 세분화가 크게
좋아 보였음(19.4%p -> 6.6%p) - 하지만 이건 커버리지가 100%->20%로 줄면서 "매칭되는
쉬운 주문만 남긴" 착시(vendor_cat/배송지 검증과 같은 유형). 공정 비교를 위해
**카스케이드(세분류->소분류->중분류->대분류 순차 폴백, 매칭 실패 시 기존 cat으로
자동 하강)** 구조로 재검증 - 같은 주문 7,102건(cat 모집단) 전후 비교, 전체 day-mark(1~30일).

### 결과 (cat 모집단 7,102건, 같은 주문 전후 비교)
```
day     기준(대분류만)  카스케이드  cat_4만추가
1일        6.7p        8.0p       8.1p    <- 단기는 오히려 악화
3일       15.6p       16.2p      16.1p    <- 악화
7일       19.4p       19.2p      19.3p    <- 동일
14일       8.9p        8.3p       8.5p    <- 미세 개선
21일       3.3p        2.9p       2.8p    <- 미세 개선
30일       3.4p        3.5p       3.4p    <- 동일
```
- cat_4(세분류 완전일치, 1,431건)는 실제로 정확함(7일 6.6p) - 그러나 이들이 빠져나간
  잔여 주문(5,671건)의 오차가 19.4p->22.5p로 나빠져 합계가 상쇄됨. "세분류가 정확한 건
  그 상품군이 원래 예측하기 쉬운 것들이라서"이지, 세분류 정보가 새 정보를 주는 게 아님.
- 중간층(cat_3=소분류까지 18.0p, cat_2=중분류까지 20.0p)은 기존 대분류만큼 나빠서
  성적 나쁜 중간층을 빼고 cat_4만 넣는 변형도 검증했으나 결과 동일(순이득 없음).

### 결론
**반영하지 않음.** "더 세밀한 분류가 더 정확하다"는 가설이 이 데이터에서 세 번째로
반증됨(1. vendor_cat 제거, 2. 관리회계 재분류 기각, 3. 카테고리 카스케이드 기각).
본부장 보고 시: "지시하신 4단계 세분화를 실측 검증했고, 세분화가 잘 맞는 일부(20%)는
좋아지지만 나머지 80%가 그만큼 나빠져 순이득이 없었다"고 근거와 함께 보고 가능.

### 재해석 - 조건부 개선안으로 부활 (2026-07-13, 사용자 제안)
"쉬운 주문만 골라내고 어려운 주문은 예측 자체를 포기(숨김/'산정 중' 표시)하면 어떤가"
라는 사용자 제안으로 판정 기준이 달라짐: 목표가 "모든 주문의 평균 정확도"에서 "**보여주는
예측은 전부 정확하게**"로 바뀌면, cat_4(세분류 완전일치) 층은 전체 오차를 못 줄여도
"콜드스타트 중 자신 있게 보여줄 수 있는 20%(1,431건, 전 구간 오차 6.6%p 이하)를 골라내는
분류기"로 유효함. 숨김/산정중 UI 정책은 이미 API_SPEC.md 5-2번 협의 옵션(①/③)에 있고,
그 정책이 채택되면 cat_4 덕분에 숨김 대상이 콜드스타트 4.7% -> 4.4%로 줄어듦.
**지금은 반영하지 않고**(정책 미확정 - 옵션 ② 채택 시 cat_4는 무의미해짐), API_SPEC.md
5-2번에 조건부 개선안으로 문서화함.
**의사결정 주체(2026-07-13 사용자 정정)**: "예측을 포기(숨김)할지 말지"는 UI 구현
디테일이 아니라 서비스 정책 결정(고객에게 무엇을 약속할 것인가)이므로 **김정훈 본부장
결정 사안**임 - 박형근 차장과는 그 결정 이후의 구현 방식을 협의하는 순서. 트리거:
본부장이 숨김/산정중 정책(옵션 ①/③)을 채택하면 cat_4 반영 검토.
이 재해석은 본부장이 정의한 과제 목적("정확한 도착일 한 점이 아니라 불확실성의 정량화 및
전달")과 정합 - 틀린 확신을 보여주는 것보다 정직한 "산정 중"이 낫다는 방향.

## MIN_N 하향 검증 - 실익 없음, 반영 안 함 (2026-07-10, 본부장 지시 사항 검증)

### 배경
본부장 검토 미팅에서 "sku=200/나머지=1000 기준이 과한 것 아니냐, 낮추면 더 많은 품목이
포함돼 오차를 줄일 수 있지 않겠냐"는 지시가 나와 실제 검증함. MIN_N 후보
1000(현재)/700/500/300과 SKU_MIN_N 200/150/100/50을 같은 비율로 낮춰가며 2026H1
홀드아웃으로 비교.

### 결과
```
MIN_N=1000(현재): 전체 오차범위 0.07~1.27%p, vendor 7일오차 0.0%p
MIN_N=700:        전체 오차범위 0.03~1.37%p, vendor 7일오차 0.3%p
MIN_N=500:        전체 오차범위 0.07~1.41%p, vendor 7일오차 1.0%p
MIN_N=300:        전체 오차범위 0.01~2.78%p, vendor 7일오차 1.5%p
```
MIN_N을 낮출수록 전체 오차 범위와 vendor 레벨 오차가 계속 악화(단조적).

### 급성장 세그먼트 재발 확인 (04_recency_diagnosis.py에서 MIN_N=1000으로 올린 원인 재검증)
vendor(협력사 전체) 단위로는 급성장 협력사 대부분이 이미 MIN_N=1000에서도 편입돼 있어
안 보였지만, vendor_mid(협력사x중분류) 세부 조합으로 다시 보면 **MIN_N=300에서 새로
편입되는 "파일럿->대량 폭증형" 조합이 110개** 발견됨(2023~2025 train n<1000인데
2026H1 물량이 5배 이상 급증). 대표 사례:
```
원창유통x식품:   train n=495   2026물량=73,619  성장률149배  실제오차=2.4%p(양호)
알파x사무용품:   train n=358   2026물량=42,299  성장률118배  실제오차=7.1%p(문제)
```
정확히 MIN_N을 30->1000으로 올렸던 원래 원인(원창유통 사례, 캘리브레이션 12.7%p 왜곡)과
같은 유형의 패턴이 재발 - 일부는 우연히 괜찮아도(원창유통) 다른 조합은 여전히 큰 오차를
보임(알파 7.1%p).

### 결론
**반영하지 않음.** 커버리지 증가의 이득보다, MIN_N=1000을 만든 근본 원인(급성장
세그먼트 오채택)이 그대로 재발하는 리스크가 더 큼. 본부장 지시사항 검증 완료, 실측
근거로 현행 유지 결정.

### 후속: sku만 단독 하향도 검증 - 역시 반영 안 함 (2026-07-13)
사용자 지적("위 검증은 sku와 나머지를 동시에 낮춰 분리가 안 됐고 day7만 봤다")이 맞아서,
SKU_MIN_N만 200->150/100/50으로 낮추고 나머지 레벨은 1000 고정으로 전 구간(1~30일) 재검증.
- 집계상으로는 무해해 보였음: sku 커버리지 52.7%->69.5%, sku 레벨 평균 오차 유지.
- 그러나 **같은 주문 counterfactual**(새로 sku로 승격되는 74,914건에 기존 예측과 sku
  예측을 동시 적용)에서 진실이 드러남: **9개 day마크 중 7개에서 기존(vendor 등) 예측이
  더 정확**(예: day2 0.9p vs 2.4p, day5 1.9p vs 2.9p). 집계가 무해해 보인 건 기존
  안정 sku들이 평균을 지탱했기 때문 - 새로 편입되는 소표본 sku(50~200건)는 자기 협력사
  평균보다 못한 예측을 만듦. vendor_cat 제거 때와 같은 결론: **표본이 작으면 "자기
  데이터"가 "더 큰 그룹 데이터"보다 부정확하다.**
- 급성장 sku 재발도 소규모 확인(2개, 오차 8~10%p).
- **교훈**: 집계 평균이 안 나빠져도 same-order counterfactual은 반드시 확인할 것 -
  구성비 변화가 문제를 가릴 수 있음.

## vendor_mid 추가 개선 - 2018~2021년 데이터까지 확장 반영 완료 (2026-07-10)

```

day 7: 2.7%p -> 0.8%p
day14: 4.4%p -> 2.9%p
day21: 8.6%p -> 7.0%p

### 구현
- 2018~2021 데이터는 표준 `data_loader.py`가 모르는 별도 폴더/파일명 패턴("_전량입고"
  접미사)과 축소된 컬럼셋(109개 -> 10개, 표준납기일/출하일자 등 없음)이라 전용 로더
  `03_distribution_fit.py`의 `load_old_vendor_mid_data()`를 추가(파싱 시간이 길어
  `cache/old_2018_2021.parquet`로 캐싱). `표준납기일` 컬럼은 없어서 NaT로 채움 -
  `표준납기_lt`가 전부 NaN이 되지만 vendor_mid 테이블 구축(lt만 사용)엔 영향 없음.
- `VENDOR_MID_TRAIN_YEARS`를 `[2018,...,2025]`로 확장, `main()`에서 최신(2022~2025,
  표준 로더)과 구버전(2018~2021, 전용 로더)을 각각 로드 후 concat해서 vendor_mid만
  재계산 - sku/vendor/cat/global은 그대로 2023~2025 유지.
- 세그먼트 수(이 시점 기준): 2,171(sku)+631(vendor_mid)+197(vendor)+50(cat)+1(global) = 3,050개
  (이후 2026-07-13 표준납기 버킷 레벨 추가로 3,169개로 갱신됨 - 아래 항목 참고).

### 파일 읽기 관련 주의사항 (실수 기록)
이 폴더의 xlsx를 처음 openpyxl `read_only=True` + `iter_rows`로 열었을 때 컬럼이 1개
("상품코드")만 있는 것처럼 잘못 읽혀서, "이 파일은 상품코드 목록뿐이라 못 쓴다"고
잘못 판단했었음 - 사용자가 직접 파일을 열어 다른 컬럼도 있다고 정정해줘서
`pandas.read_excel`(engine=openpyxl, read_only 아님)로 다시 읽으니 25개 컬럼이 정상
확인됨. **원인 미규명**(이 특정 파일 구조에서 read_only 모드가 컬럼을 잘못 인식하는
버그로 추정) - 앞으로 이 폴더 또는 유사 대용량/오래된 xlsx 파일을 openpyxl read_only로
읽어서 "컬럼이 이상하게 적다"는 결과가 나오면, 결론 내리기 전에 반드시
`pandas.read_excel`로 교차 확인할 것.

## 표준납기일(SLA) vs 모델 예측 불일치 - 검토 완료, 의사결정 필요 (2026-07-09)

### 배경
사용자 우려: 고객에게 이미 노출 중인 "표준납기일"과 모델 예측이 차이 나면("표준납기일 5일인데
모델은 10일") 신뢰 문제가 생길 수 있음. 5일 이상 차이만이 아니라 "차이 나는 것 자체"가
문제일 수 있다는 지적으로 전체 분포를 재확인함(`11_sla_gap_check.py`, 결과는
`sla_gap_analysis.csv`/`sla_gap_report.txt`).

### 검증 결과 (2026H1 홀드아웃, SLA 데이터 있는 sku 1,739개 기준)
```
3일 이상 빠름(SLA 보수적): 19.6% (물량 23.87%)
1~2일 빠름:              30.5% (물량 36.96%)
정확히 일치:              22.3% (물량 19.11%)
1~2일 늦음(경미):         14.3% (물량 10.46%)
2~5일 늦음(중간):          6.4% (물량  4.47%)
5일 초과 늦음(주의):        7.0% (물량  5.12%)
```
모델이 SLA보다 빠르게 예측하는 경우가 50.1%로 오히려 더 많음 - **표준납기일 자체가
전반적으로 보수적(안전마진 있게)으로 잡혀있다**는 뜻. "늦게 예측"되는 27.7%(물량 20%) 중에도
과반(14.3%)은 1~2일의 경미한 차이. 정말 눈에 띄는 차이(5일 초과)는 7.0%(물량 5.12%)뿐.

**이 5일 초과 그룹(121개 SKU)의 95.9%가 이미 Kraljic 분류상 전략재/병목재(공급위험 高)** -
영풍기획 CS전용 물품, UTP케이블류 등 이미 "배치성 발주" 패턴으로 식별된 상품군과 정확히
겹침. 즉 큰 불일치는 무작위 노이즈가 아니라 이미 알려진 특정 상품군에 집중돼 있음.

**(2026-07-10 재확인)** 2025/2026 raw data 최신화(홀드아웃 40.3만->44.7만 건) 후 다시
돌려도 결론 동일: 5일 초과 그룹 122개(7.0%, 물량 5.14%), 전략재+병목재 비율 95.1% -
표본이 늘어도 패턴이 흔들리지 않음을 확인.

### 검토한 두 가지 대응안과 판단
1. **모델 예측을 SLA에 맞춰 조정** - 채택 안 함. 실제로는 27일 걸리는 상품을 SLA에 맞춰
   "7일"이라고 보여주면, 실제로 늦게 도착했을 때 신뢰 문제가 오히려 더 커짐. 이 프로젝트가
   지켜온 "검증된 값만 반영, 임의 왜곡 금지" 원칙에도 위배됨(공휴일 보정/shortage_flags와
   동일 철학).
2. **표준납기일 자체를 변경** - 이 프로젝트 단독으로 결정할 사항 아님. 표준납기일은 이
   배송예측 프로젝트만의 필드가 아니라 기존 SLA 준수율 KPI 등 다른 시스템에서도 쓰이고
   있을 가능성이 높아, 구매팀/계약 담당 부서와 별도 협의가 필요한 정책 변경. 다만 50.1%
   구간(모델이 SLA보다 빠름)은 SLA를 더 타이트하게(경쟁력 있게) 재조정할 기회로 검토해볼
   가치는 있음 - 근거자료로 `sla_gap_analysis.csv` 활용 가능.

### 이번 프로젝트 범위에서 제안하는 대응
모델 예측도 왜곡하지 않고 SLA도 임의로 바꾸지 않는 절충안: **gap 크기에 따라 화면 표시를
차등화**. gap<=2일은 그대로 노출(경미한 차이는 체감 오차 범위), gap>2~5일부터는 표준납기일과
모델예측을 나란히 보여주며 안내 문구 추가, gap>5일(이미 Kraljic 고위험군과 겹침)은 별도
설명("협력사 사정상 표준 안내보다 오래 걸릴 수 있음") 노출을 검토. shortage_flags와 같은
패턴으로 확장 가능한 설계 - API_SPEC.md의 "통합플랫폼팀과 확인이 필요한 부분"에 추가함.

## HOLIDAYS 리스트를 수동 관리 -> holidays 라이브러리로 전면 교체 (2026-07-08)

### 배경
"12월 1일 주문에 연말 계절성이 반영되나" 질문을 계기로 HOLIDAYS 리스트가 2026-06까지만
있어 하반기 전체가 빠졌던 걸 발견(바로 위 별도 항목 아님, 같은 날 후속 조치). 수동
리스트의 구조적 한계(매년 갱신 누락 위험, 음력 공휴일 근사치, 임시공휴일/선거일 누락)를
근본적으로 해결하기 위해 `holidays` 파이썬 라이브러리(사내망에 이미 설치돼 있어 인터넷
불필요, 버전 0.99)로 전면 교체.

### 검증 과정에서 있었던 일 (중요 - 지식 검증 실패를 스스로 잡은 사례)
제헌절(7/17)을 "2008년 폐지돼서 실제 휴무 아님"이라고 판단해 필터링하려다가, 사용자가
"확인이 필요하다"고 제동을 걺 -> 실제로 웹 검색해보니 **2026년 7월 17일부터 18년 만에
법정공휴일로 재지정**된 것으로 확인됨(다음뉴스/위키트리/국제뉴스 등 복수 출처 확인).
그리고 `holidays` 라이브러리를 실제로 조회해보니 **이미 이 연도별 차이를 정확히
반영**하고 있었음(2023~2025는 제헌절 없음, 2026부터 정확히 있음) - 라이브러리 자체가
이미 검증된 소스라는 근거가 됨. 이 사례가 남기는 교훈: "상식적으로 아는 것"도 law/제도
변경 가능성이 있으면 검증 없이 필터링하면 안 됨 - 오래된 지식으로 실제 공휴일을
놓칠 뻔했던 사례.

### 구현
`08_holiday_adjustment.py`에 `_build_holidays_dynamic(years)` 함수 추가 - `holidays.KR()`이
반환하는 개별 날짜를 연속 날짜끼리 묶어서 기존 (시작일, 종료일, 이름, 신뢰도) 형식으로
변환. `HOLIDAYS = _build_holidays_dynamic(range(2023, date.today().year + 3))`로
매 실행마다 자동으로 범위가 넓어지게 함 - "리스트가 짧아서 최근 반년이 빠지는" 사고가
구조적으로 재발하지 않음.

### 재검증 필요했던 것 - ADJUSTABLE_DAYS_BY_BUCKET
라이브러리 교체로 single 버킷의 실제 사례 수가 16,262 -> 25,734건으로 늘어남(임시공휴일/
선거일 등 다양한 공휴일이 추가로 잡힘). 이 때문에 안전 구간이 달라짐:
```
(2026-07-08, 수동 리스트 22건 기준) single: day1~10 개선
(2026-07-08, holidays 라이브러리 25,734건 기준) single: day1~3만 개선, day5부터 악화
  day3: 미보정오차 13.7%p -> 보정후 0.2%p (오히려 더 좋아짐)
  day5: 미보정오차 7.2%p -> 보정후 7.9%p (악화)
  day7: 미보정오차 3.0%p -> 보정후 6.0%p (악화)
```
표본에 효과 크기가 제각각인 다양한 공휴일이 섞일수록 안전 구간이 좁아지는 경향으로
보임. `ADJUSTABLE_DAYS_BY_BUCKET["single"]`을 `{1,2,3,5,7,10}` -> `{1,2,3}`으로 축소.
**HOLIDAYS 소스가 바뀌면 이 안전 구간도 반드시 재검증할 것** - 자동으로 따라오지 않음.

### 검증 완료
`serve.py` 스모크 테스트: 12/1(신정과 무관) `holiday_adjusted=False`, 12/30(신정 하루전)
`holiday_adjusted=True`(day1~3만 조정, day5부터 원래 값), 7/15(제헌절 이틀전, 2026년
신규 재지정) `holiday_adjusted=True` 정상 확인.

### 남은 참고사항
- `holidays` 라이브러리가 혹시 실제 물류 지연과 무관한 날짜(예: 상징적 국경일)를 포함해도,
  홀드아웃 검증에서 효과 없으면 자동으로 무보정(1.0) 처리되므로 안전 - 임의 사전 필터링
  불필요(제헌절 사례로 이미 확인).
- 이 라이브러리 자체도 법 개정을 실시간 반영하는 건 아니고 패키지 업데이트에 의존함 -
  아주 최근에 결정된 임시공휴일 등은 라이브러리가 아직 모를 수 있음. 매번 재실행 시
  라이브러리 버전이 최신인지 정도는 가끔 확인할 것.
- 이 작업으로 `known_risks.md`의 기존 "음력 공휴일 근사치" 관련 경고들은 더 이상
  유효하지 않음(정확한 날짜로 대체됨) - 아래 "공휴일 근접 보정" 항목의 관련 문구는
  구버전 설계 기록으로 남겨두되 현재는 해당 없음.

## 원 질문 완결: "12월 초 예산 소진 몰림"·"여름 폭우 수요"도 배송 지연과 무관 (2026-07-08)

### 배경
사용자가 처음 물었던 계절성 질문은 두 가지: ①"12월 초부터 시작되는 연말 예산 소진으로
인한 주문 몰림", ②"여름 장마/태풍 수해로 인한 특정 품목 수요 급등". 공휴일 보정
(신정 직전 1~3일 등)을 "연말 계절성 반영"이라고 표현한 적이 있었는데, 이건 범위가
완전히 다르다는 지적을 받고(위 항목 참고) 두 원 질문을 직접 검증함.

### 검증 1: 12월 전체 (train 2023-2025, 자체 비교 - 홀드아웃엔 12월 데이터 없음)
```
12월 (n=256,974, 12개월 중 물량 2위): 3일=51.7%  7일=85.6%  14일=95.3%  median=3.0일
가장 느린 달: 10월(7일=77.8%), 9월(7일=79.8%), 4월(7일=80.1%)
```
12월은 물량이 많은데도(2위) 배송 속도는 오히려 상위권 - "몰림은 있지만 지연은 없음".

### 검증 2: 우산/장화/우비 (장마철 프록시, 서비스카테고리 리프 경로에 "우산|장화|우비"
포함된 것 전체 - 대분류/중분류 이름이 여러 체계로 흩어져 있어 리프 문자열 검색으로
우회, known_risks.md의 카테고리 개편 항목과 같은 이유)
```
6월(장마 초입) n=1,278건으로 상반기 중 최고 물량, 하지만 11월(1,465)/12월(1,264)이 더 많음
6월 배송속도: 3일=57.9%, 7일=92.6% (평이~양호, 최악은 아님)
가장 빠른 달: 11월/12월 (3일 71~74%) - 물량 제일 많은 달이 오히려 제일 빠름
```
이 카테고리엔 "안전화/장화"(공사장 작업화)도 섞여 순수 장마 수요만은 아니지만, 그걸
감안해도 "여름 급증 -> 배송 지연" 패턴은 안 보임.

### 결론 - 세 번째 일관된 패턴
계절가전(known_risks.md 아래 항목), 12월 전체, 우산/장화 세 가지 모두 "물량 급증은
있지만 배송 지연으로 이어지지 않는다"는 같은 결론으로 수렴. 이 모델(협력사×상품군
단위 확률 pooling)이 이미 3년치 데이터를 통째로 학습해서 계절 변동을 어느 정도
암묵적으로 흡수하고 있거나, KT커머스/협력사 쪽 물류 처리 능력이 이 정도 계절 변동은
버텨내는 것으로 추정 - 어느 쪽이 진짜 이유인지는 확인 안 됨(추가 검증 없이는 확정 불가,
우선순위 낮음).

**사용자 원 질문에 대한 최종 답**: "12월 예산 소진 몰림"과 "여름 폭우 수요 급등" 둘 다
검증했고, 둘 다 배송 지연 효과를 찾지 못했다 - 반영할 게 없다는 뜻. 공휴일 직전 1~3일
보정(신정/광복절 등)은 이 두 질문과 별개의, 더 좁은 범위의 개선이었다.

## 계절성(여름 수요 급증) 및 카테고리 체계 개편 - 검증했으나 반영 안 함 (2026-07-08)

### 배경
"여름 장마/태풍 수해, 더위로 인한 수요 급등"이 배송 지연을 유발하는지 검토(연말 예산
소진 부분은 "하루짜리 공휴일 보정" 항목에서 별도 확인·반영 완료). 가장 유력한 후보인
"계절가전"(에어컨/선풍기/온풍기/제습기/가습기/공기청정기/전기장판)으로 검증.

### 발견 1: 카테고리 체계가 2025-12-29에 개편됨 (사용자 확인)
정확히 같은 이름("가전/전자제품")으로 검색하면 train(2023-2025) 55,715건 vs
holdout(2026H1) 236건으로 안 맞았음 - 사용자가 "2025년 대비 2026년에 카테고리 체계를
개편했다"고 확인하고 매핑 참고자료(`서비스 카테고리 담당자 관리회계.xlsx`)를 공유해줌.
대분류도 바뀜: train은 "전자제품"(55,622건), holdout은 "가전"(11,786건)이 대세.

### 발견 2: 계절가전도 실제로 여름에 급증하지만, 성수기가 오히려 더 정확함
매핑 파일로 신/구 taxonomy를 다 포괄하는 "계절가전" 그룹을 만들어 검증(train 5,842건,
holdout 1,050건, 대부분 vendor 레벨로 응답):
```
월별 물량(2026H1): 1월 115 → 2월 63 → 3월 103 → 4월 106 → 5월 232 → 6월 431 (여름 급증 확인)
월별 day7 오차:     1월 5.0%p  2월 19.0%p  3월 2.5%p  4월 6.4%p  5월 4.3%p  6월 2.9%p
```
성수기(6월)가 가장 정확하고(2.9%p), 비수기(2월)가 가장 부정확함(19.0%p, 다만 설날과
겹쳐 표본도 작음 n=63) - **가설과 정반대**. 해석: train 3년치 데이터 자체가 이미
"6월에 물량이 몰린다"는 패턴을 담고 있어서(6월 관측치가 많아 평균에 강하게 반영),
vendor 레벨 예측이 자연스럽게 성수기 패턴 쪽으로 이미 기울어 있음 - 명시적 계절
보정 없이도 물량 가중 평균 덕분에 성수기가 암묵적으로 잘 맞음.

### 발견 3: 카테고리 체계 불안정성 자체를 "관리회계" 필드로 해결 시도 - 기각
사용자 제안으로 대분류/중분류 대신, 매핑 파일의 "관리회계"(연도 개편에도 안정적인
필드)로 cat 레벨을 다시 만들어 같은 주문 기준 counterfactual 검증:
```
(같은 주문 n=1,526) day3: 기존cat 22.3p vs 관리회계cat 25.2p / day7: 36.6p vs 40.9p / day10: 37.7p vs 41.5p
```
전 구간에서 기존 대분류 방식이 명확히 더 정확함 - 관리회계 분류가 61개(구)/35개(신)로
너무 성기게 묶여서 배송 속도가 다른 품목들이 섞인 게 원인으로 보임(vendor_cat 사례와
같은 유형: "이름이 안정적"과 "예측이 정확"은 별개). 매핑 성공률도 완벽하지 않음
(train 87.3%, holdout 78.1%).

**왜 실패했는지 원인 확인(2026-07-08, 사용자 확인)**: old->new 카테고리는 단순 개명이
아니다 - "개편하면서 상품코드에 잘못 등록된 오래된 카테고리를 올바르게 수정하기도
했다"(사용자). 즉 old 카테고리의 관리회계/중분류가 new의 무엇에 대응하는지는 **근본적으로
추정일 뿐 정확한 매핑이 아니다** - 일부는 순수 개명이지만 일부는 실제 재분류(오분류
수정)라서 "이름이 비슷하면 같은 것"이라는 가정 자체가 깨진다. 이게 위 counterfactual
검증에서 관리회계 방식이 진 실제 이유로 보임 - 성긴 분류 문제뿐 아니라 매핑 자체의
정확도 한계가 같이 작용한 것. 참고로 확인된 사실: 관리회계 체계는 필요할 때 임의로
바뀌지만 빈도는 낮음(전사적 변경이 필요해서), 이번 매핑 파일은 카테고리 전체를
담은 것(파일 누락으로 인한 매핑 실패 아님), 카테고리는 회계연도 내에서 거의 안
바뀌고 극소수만 예외적으로 바뀜(2025-12-29는 단일 개편 이벤트로 봐도 무방).
**결론: 매핑 방식을 바꿔서 재시도해도 개선 가능성 낮음** - 이미 검증한 접근(이름
유사도 기반 매핑)이 사용자가 확인해준 방식과 동일했고, 그 결과가 실패였음.

### 결론
- 여름 수요 급증 → 배송 지연 가설: 기각(계절가전에서 반대 결과 확인)
- 관리회계 기반 cat 재분류: 기각(기존 대분류 방식이 더 정확)
- 카테고리 체계가 개편된 건 사실이지만, 지금까지 검증한 바로는 cat 레벨 정확도에
  실질적 악영향은 확인 안 됨 - 추가 조치 불필요
- (2026-07-09 해결) ~~"여름 장마/태풍 수해" 관련 카테고리(우산/장화 등)는 이번엔 확인
  못함~~: 이후 우산/장화/우비로 별도 검증 완료 - 계절가전과 같은 결론(물량 급증, 배송
  지연 없음). 위 "원 질문 완결" 항목(59번째 줄) 참고.

## gui_predict.py 마감시간 로직의 토요일 처리 - 확정 완료 (2026-07-08 결정, 2026-07-15 업무 사실 확인)

### 배경
`gui_predict.py`의 마감시간(`CUTOFF_HOUR=15`) 로직이 원래 요일을 안 가리고 "+1일"만
했는데, 이러면 토요일 마감 이후 조회 시 "내일"이 일요일(배송완료의 0.43%뿐 - 사실상
휴무)로 계산되는 버그가 있었음. 고치면서 "토요일도 같이 건너뛸지"가 애매한 지점으로
드러남 - 토요일은 배송완료의 9.8%를 차지할 만큼 실제로 돌아가는 날이지만, 이게
"협력사가 토요일에 신규 발주도 접수한다"는 뜻인지 "금요일까지 접수된 건이 토요일에
배송만 완료된다"는 뜻인지는 배송완료 데이터만으로 구분이 안 됨.

### 처리
1차로 추측하지 않고 `AskUserQuestion`으로 명시적으로 물어봄 - 사용자가 **"월요일로
건너뜀(보수적)"**을 선택(2026-07-08). 그래서 지금 코드는 금/토/일 마감 또는 토/일
자체 접속 시 전부 다음 월요일로 계산한다(`CUTOFF_HOUR` 주석 및 `on_search()` 참고).

### 확정 (2026-07-15)
사용자 확인: **토요일에 신규 발주는 접수되지 않음.** 추가로, 설령 협력사에 따라
예외적으로 접수되는 경우가 있더라도 "접수 안 됨"을 기본 가정으로 유지하기로 함 -
이걸 확인하려면 협력사마다 개별 확인이 필요한데 현실적으로 전수 확인이 불가능하기
때문(정책적 보수적 가정). 즉 현재 로직(토요일도 월요일로 건너뜀)이 데이터 검증이
아닌 사용자 판단이었던 상태에서, 이제 업무 사실 확인 + 정책 확정으로 종결됨 - 통합
플랫폼(박형근 차장) 협의 시 재확인 불필요.

## 대량주문/동일주소 몰림(버스트) 지연 가설 - 검증했으나 효과 없음 (2026-07-08)

### 가설
"한 번에 발주수량이 크거나, 비슷한 시기에 같은 발주자/동일주소로 대량 발송을 요청하면
배송이 지연되지 않을까" - 원본 데이터에 `수량`, `주문자아이디` 필드가 실제로 존재함을
확인하고 검증(단, 둘 다 `data_loader.py`의 USECOLS엔 없어서 2026년 KT 세그먼트만
원본 엑셀에서 별도로 읽어 검증 - 87,100행 -> 유효 75,223건).

### 검증 1: 수량이 많을수록 느려지는가
물량 많은 상위 8개 상품코드만 눈으로 봤을 때는 들쭉날쭉해 보였음(소량 대비 대량 3일이내
도달률: -31%p ~ +9.7%p 범위) - 표본을 26개 상품코드(n≥200)로 넓혀서 상품코드 내
수량순위와 lt의 상관계수를 계산하니 평균 0.039(사실상 0), 양의 상관 30.8% vs 음의
상관 26.9%로 방향성 자체가 없음. 처음 8개에서 보였던 패턴은 우연(노이즈)이었음 -
표본이 적을 때 눈으로 본 패턴을 성급히 신뢰하면 안 된다는 사례가 또 확인됨.

### 검증 2: 동일 주문자x배송지가 짧은 기간(±3일)에 몰리면 느려지는가
단독 주문(그 기간에 1건만, n=8,507) 3일이내 도달률 58.2% vs 몰림 주문(그 기간에 5건
이상, n=53,273) 54.3% - 차이 3.9%p로 작고, median_lt은 둘 다 3일로 동일. 게다가
"5건 이상 몰림"이 전체의 86%(53,273/61,780)를 차지할 정도로 이 데이터에서는 흔한
패턴(사무실/부서 단위 반복 발주가 일상적)이라, "이상 몰림"이라기보다 정상적인 주문
행태에 가까움 - 버스트 정의 자체가 이 도메인엔 안 맞았을 수 있음(트리거 참고).

### 결론
두 가설 다 반영할 근거를 찾지 못함 - 배송형태/배송지 축과 같은 결말. cat/global
콜드스타트 문제뿐 아니라 이 프로젝트 전반적으로 "지금까지 시도한 주문 시점 정보
축들은 대부분 뾰족한 신호가 없다"는 패턴이 반복되고 있음(known_risks.md의
"cat/global 콜드스타트 세분화 시도" 항목도 참고).

### 트리거 (재검토 여지)
- 버스트 정의(±3일, 5건 기준)를 다르게 잡으면(예: 같은 날 동일 상품코드 대량 1건
  주문 vs 여러 날에 걸친 소량 반복 주문을 구분) 다른 결과가 나올 수 있음 - 지금은
  "몰림"을 너무 넓게 정의했을 가능성 있음
- 협력사 쪽에서 "특정 규모 이상 주문은 처리에 며칠 더 걸린다"는 실무 확인이 있다면
  재검증 가치 있음(지금은 순수 데이터 탐색이라 실무 지식 없이 진행함)

## 하루짜리 공휴일(신정/광복절 등) 보정 누락 - single 버킷 추가 (2026-07-08)

### 표현 주의 (2026-07-08 재확인)
이 항목을 "연말 계절성 반영"이라고 부르면 부정확함 - **정확히는 "공휴일 직전 1~3일"에만
적용됨**(PRE_HOLIDAY_WINDOW=3). 예: 신정(1/1) 관련 보정은 12/29~31 주문에만 적용되고,
12/1처럼 신정까지 한 달 가까이 남은 주문에는 전혀 적용 안 됨(직접 확인: `serve.py`로
12/1 조회 시 `holiday_adjusted=False`). 사용자가 원래 질문한 "연말 예산 소진으로 인한
넓은 기간의 주문 몰림"(12월 초~중순 포함 가능)은 이 보정과 범위가 다르고, 검증도 반영도
안 된 상태 - 미팅 등에서 "연말 계절성 반영 완료"라고 뭉뚱그려 말하지 말 것.

### 배경
사용자가 "수요 계절성(여름 수해/더위, 연말 예산 소진)을 검토했는지" 질문 -> 이 프로젝트는
배송 소요시간을 예측하는 것이지 수요량을 예측하는 게 아니라서 계절성 자체는 원래
스코프 밖이지만, "수요 급증이 실제 배송 지연을 유발하는 효과"는 관련이 있어 재점검함.
`07_calendar_effects_check.py`가 이미 만들어둔 "이상일"(비정상적으로 배송이 느려진 날)
목록을 다시 보니 **8월 12~14일이 2023~2025년 3년 연속**, **12월 31일이 2024~2025년
2년 연속** 이상일로 잡혀 있었음(-27~-61%p).

### 원인 확인
`08_holiday_adjustment.py`의 `MIN_HOLIDAY_LEN=2` 필터가 "2일 이상 연속 휴일이어야
물류센터가 실제로 멈춘다"고 보고, **광복절(8/15)·신정(1/1) 같은 하루짜리 공휴일을
전부 보정 대상에서 제외**하고 있었음. 그런데 실측해보니(train 2023~2025):
- 광복절 직전 3일(n=19,490): day2 도달률이 평소 37.3%->15.2%(비율 0.408)로 급락
- 신정 직전 3일(n=9,293): day2 도달률이 평소 37.2%->17.4%(비율 0.467)로 급락
표본도 충분하고 효과 크기도 기존에 이미 보정 중이던 연휴들과 비슷하거나 더 큼 -
"하루짜리는 무조건 제외"가 틀린 기준이었음.

### 수정
`08_holiday_adjustment.py`에 `single`(1일) 버킷을 신설(`short`=2~3일, `long`=4일+와
별도 관리). 홀드아웃(2026H1) 검증 결과 **single 버킷은 day1~10까지 보정이 개선**됨
(day7 오차 4.4%p->1.4%p, day10 5.8%p->3.4%p) - 기존 short/long이 day1~5까지만
안전했던 것과 다른 패턴이라, 버킷별로 안전 구간을 따로 관리하는
`ADJUSTABLE_DAYS_BY_BUCKET`(single={1,2,3,5,7,10}, short/long={1,2,3,5})로 교체.

`serve.py`의 `_holiday_ratio_for_day()`에도 연쇄 버그가 있었음 - "day5 이하만 보정"이
하드코딩되어 있어서, single 버킷의 새 day7/10 보정값이 매일 단위 headline 계산(fine-day
보간)에서 무시될 뻔했음. 검증 안 된 날은 `holiday_adjustment_ratios.csv` 저장 시 이미
`applied_ratio=1.0`으로 박아두므로, 이 하드코딩 컷오프 자체가 불필요했음 - 제거하고
"바로 아래 DAY_MARK 값 사용"만 남김.

### 검증
`serve.py` 스모크 테스트(2025-12-30 주문, 신정 직전): `holiday_adjusted=True`, day7
확률이 정확히 비율만큼 하향 조정(0.964*0.9315≈0.898, 실제 출력 0.8981), headline의
fine-day 보간(day8)도 day7 비율을 정확히 상속받아 적용되는 것 확인.

**추가 검증(2026-07-08) - single 버킷을 "모든 하루짜리 공휴일"로 일반화한 게 정당한지**:
`build_holiday_starts()`는 광복절/신정만 하드코딩한 게 아니라 `length==1`인 모든
공휴일(개천절/광복절/부처님오신날/삼일절/성탄절/신정/어린이날/한글날/현충일, 총 23개
인스턴스)을 single 버킷으로 자동 분류한다. 이게 정당한지 개별 인스턴스별로 쪼개서
확인: **day2 비율이 22개 중 22개 전부 1.0 미만**(0.041~0.952, 예외 없음 - 공휴일
종류와 무관하게 "직전엔 느려진다"는 방향이 일관됨), day3도 22개 중 19개가 1.0 미만
(나머지 3개는 1.02~1.12로 노이즈 수준). 크기는 공휴일마다 다르지만(개천절 0.041처럼
극단적, 성탄절 0.952처럼 약함) 방향이 뒤집히는 사례가 없어서, 기존 short/long
버킷도 서로 다른 공휴일(설날/추석 등)을 하나로 묶어 평균 비율을 쓰는 것과 같은
방식으로 취급해도 안전하다고 판단. 실제 2026H1 홀드아웃 검증(n=16,262)도 신정+
어린이날+현충일 조합으로 이뤄진 것이라(광복절은 2026H2라 아직 미포함), 처음
수동 확인했던 광복절/신정과는 다른 조합에서도 개선이 재현된 셈 - 더 튼튼한 근거.

### 남은 참고사항
- 2026년 하반기 공휴일(광복절 8/15, 개천절 10/3, 한글날 10/9, 성탄절 12/25 등)이
  아직 `HOLIDAYS` 리스트에 없음 - 프로덕션 반영 전 추가 필요(기존에도 알려진 제약,
  API_SPEC.md 5번 항목 참고).
- 사용자가 원래 질문한 "여름 장마/태풍 수해·더위로 인한 수요 급등"과 "품목별 계절성"은
  이번 수정과 별개 - 이번 건은 "전사적 캘린더 근접 효과"(물류센터 처리 지연)이고,
  특정 카테고리(에어컨 등)의 계절 수요 급증 효과는 검증 안 됨. phase3_backlog.md 참고.

## cat/global 콜드스타트 세분화 시도 - 배송형태·배송지 축 둘 다 실패 (2026-07-08)

### 배경
홀드아웃의 4.7%(cat 1.6% + global 3.1%)가 cat/global 레벨로 폴백되고, 이 구간은
day마크에 따라 오차가 최대 19.7%p까지 벌어짐(known_risks.md의 "레벨별 불안정 구간"
항목 참고). "이 4.7%를 더 세분화할 다른 기준이 없는지" 검토했다.

### 시도: 배송형태 축으로 추가 세분화
가설: `배송형태`(협력사배송/당사배송/픽업배송)는 초반 리스크 점검에서 "협력사 이름만
알아도 절반 이상 짐작 가능"할 만큼 협력사별로 고정된 값임을 확인한 필드라(실제
재확인: train 기준 협력사의 98.1%가 배송형태 1종류만 씀), 주문 이력이 거의 없는
신규 협력사라도 이 값은 이미 알 수 있다 - 그래서 cat/global 내부를 이 축으로
나누면 콜드스타트 문제를 우회할 수 있지 않을까 검증.

### 결과: 실패 (구분력 없음)
```
cat 레벨 (n=6,470):    협력사배송 6,456건(99.8%), 당사배송 5건, 픽업배송 9건
global 레벨(n=12,463): 협력사배송 12,354건(99.1%), 당사배송 14건, 픽업배송 95건
```
cat/global 내부가 이미 "협력사배송" 하나로 거의 100% 쏠려있어서, 이 축으로는 사실상
나눌 대상이 없음.

### 원인 분석
당사배송/픽업배송은 물량이 크고 자리 잡은 방식이라 애초에 sku/vendor_mid/vendor
레벨에서 이미 답이 나온다. cat/global까지 떨어지는 건 거의 다 "이력이 거의 없는
군소 협력사가 자체적으로 택배를 붙인 경우"라서, 애초에 배송형태가 다 같다 -
그래서 이 필드로는 이 인구집단 내부의 차이를 설명할 수 없다.

### 시도 2: 배송지(지역) 축으로 추가 세분화
배송지 첫 토큰(시/도)으로 cat/global 내부를 나눠보니 지역별 7일 도달률이 최대
20~30%p 차이가 나서 처음엔 유망해 보였다(대구/전남 40%대 vs 경남/강원 70%대) - 다만
이건 단순 그룹 평균 비교였고, vendor_cat 제거 때처럼 **같은 주문에 두 방식(cat 단독
vs cat×지역)을 동시 적용**해서 다시 검증하니 결론이 뒤집혔다:
```
(같은 주문 기준, MIN_N=1000)
cat x 지역    vs cat 단독:    day3/7/10 지역이 근소 우위지만 개선폭 0.3~0.4%p뿐
global x 지역 vs global 단독: day3/7/10 전부 global 단독이 우위 - 지역 추가하면 악화
```
처음 본 20~30%p 차이는 "그 지역에 어떤 카테고리/협력사 주문이 몰렸는지"의 차이였지
지역 자체의 효과가 아니었음 - cat처럼 카테고리를 이미 통제하면 차이가 거의 사라지고,
global처럼 통제가 없으면 지역이 오히려 노이즈로 작용해 악화됨. vendor_cat 사례와
같은 유형의 착시(서로 다른 인구집단 비교)에 이번엔 이 검증 자체가 걸렸다가, 같은
방법론으로 다시 확인해서 바로잡음 - phase3_backlog.md 참고.

### 결론
현재 데이터로는 cat/global의 4.7%를 더 세분화할 뾰족한 기준을 찾지 못했다(배송형태,
배송지 둘 다 시도 후 기각). 이건 모델 결함이 아니라 "협력사 이력 자체가 없다"는
구조적 콜드스타트 한계이고, 어떤 주문 시점 정보로 잘라봐도 이 근본 원인으로 돌아온다.
"완성됐다"고 표현하지 말고 "현재 데이터로는 여기까지, 데이터가 늘어나면 재검토
가능"으로 열어둘 것.

### 향후 개선 방향 (Phase 3+, 모델링만으로는 해결 불가 - 데이터 확장 필요)
- 신규 협력사 온보딩 시 업종/규모 정보 수집
- 협력사 소재지 정보(배송지가 아니라 협력사 자체 위치)
- 협력사별 사전 등록 SLA
- 택배사 실적 이력을 협력사와 별개로 활용

### 트리거
- Phase 3 진입 시 데이터 확장 협의(구매팀/MD)
- 통합플랫폼 쪽에 신규 협력사 관련 추가 데이터가 있는지 확인 시(박형근 차장님 협의 때)
- cat/global 비중이 유의미하게 커질 때 재검토

## vendor_cat 레벨 제거 - 세분화가 항상 도움되는 건 아님 (2026-07-08)

### 원인
아래 "레벨별 불안정 구간" 표(2026-07-07)를 보다가 "6단계 폴백 순서가 정말 최선인가"라는
질문이 나옴. 문제는 그 표만으로는 답할 수 없다는 것 - vendor_cat으로 답한 주문과 vendor로
답한 주문은 **애초에 서로 다른 집합**이라(각자 자기 레벨에서 MIN_N을 통과한 세그먼트만
모은 것), 표를 나란히 보고 "vendor가 더 낫다/vendor_cat이 더 낫다"고 결론 내리면 표본
편향(둘의 인구 구성이 다름)에 속을 수 있음. 제대로 검증하려면 **같은 주문에 두 레벨을
동시 적용**해서 직접 비교해야 함.

### 검증 방법 (재사용 가능한 패턴)
`assign_vectorized()`로 실제 배정된 홀드아웃 결과에서 level=='vendor_cat'인 주문만 뽑고,
그 주문들의 협력사명으로 vendor 테이블에서 "만약 vendor로 답했다면 어땠을까"를 계산(merge)해서
같은 14,121건 기준으로 두 레벨의 day마크별 오차를 나란히 비교:
```
day   vendor_cat   vendor   승자
 1        0.0p      2.0p   vendor_cat
 2        1.8p      1.3p   vendor
 3        3.0p      0.8p   vendor
 5        4.7p      1.1p   vendor
 7        3.1p      1.6p   vendor
10        1.5p      0.7p   vendor
14        0.9p      0.4p   vendor
21        0.6p      1.0p   vendor_cat
30        0.4p      0.3p   vendor
```
9개 구간 중 6개에서 vendor(더 넓은 레벨)가 절대 오차로도 더 정확함 - 세분화(협력사+대분류)가
오히려 노이즈를 학습한 사례. 원래 vendor_cat을 넣을 때 참고했던 `06_category_granularity_check.py`
검증은 사실 vendor_**mid**(중분류)의 가치를 확인한 것이었고, vendor_**cat**(대분류)은 별도로
같은 방식 검증을 거친 적이 없었음.

**같은 방법으로 vendor_mid vs vendor도 확인함** (착각하지 말 것): vendor_mid는 8/9 구간에서
vendor보다 나음(day1 1.3p vs 1.7p ... day21 11.6p vs 12.3p, day30만 vendor가 근소 우위) -
vendor_mid를 vendor보다 먼저 쓰는 지금 순서는 옳았음, 제거 대상 아님.

**주의 - "상대 비교"와 "절대 기준"은 다른 질문**: vendor_mid가 vendor보다 낫다는 것과,
vendor_mid의 day21/30(11.6%p, 10.7%p)이 이 프로젝트 기준(>10%p="재검토 필요")을 통과한다는
것은 별개다. vendor_mid가 "최선의 선택"이어도 그 답 자체가 "충분히 정확"하지 않을 수 있음 -
그래서 `LEVEL_UNRELIABLE_DAYS`의 vendor_mid 항목({21,30})은 이번 vendor_cat 제거와
무관하게 그대로 유지함.

### 수정
`03_distribution_fit.py`의 `LEVELS`에서 `vendor_cat`(["협력사명","대분류"]) 제거 - 6단계에서
5단계로: sku -> vendor_mid -> vendor -> cat -> global. `serve.py`의 `_lookup()`/`__init__()`/
`LEVEL_UNRELIABLE_DAYS`/`LEVEL_CONFIDENCE`도 동일하게 정리.

## 레벨별 "불안정 구간"이 서로 다른 위치에 있음 (serve.py, 2026-07-07 확인·반영)

### 원인
cat/global 레벨(홀드아웃 4.7%)의 7일 기준 캘리브레이션 오차가 14~19%p로 커서
("재검토 필요"), UI에서 이 상품들의 확률 표시를 어떻게 할지 논의하다가 "cat/global은
완전히 부정확하니 숨기자"는 제안이 나왔음. 하지만 레벨×day마크 전 구간(1,2,3,5,7,10,
14,21,30일)을 실측 확인한 결과 훨씬 미묘한 패턴이 나옴:

```
레벨          1일    2일    3일    5일    7일   10일   14일   21일   30일
sku          0.7p   2.1p   3.1p   2.4p   1.2p   0.1p   0.5p   0.7p   0.2p
vendor_mid   1.3p   2.4p   3.3p   3.6p   3.5p   4.4p   6.0p  11.6p  10.7p
vendor_cat   0.0p   1.8p   3.0p   4.7p   3.1p   1.5p   0.9p   0.6p   0.4p
vendor       3.2p   2.2p   1.4p   1.0p   0.1p   0.4p   0.3p   0.4p   0.2p
cat          6.1p  12.5p  15.4p  19.7p  19.1p  16.7p  10.0p   4.0p   3.9p
global       2.8p   2.6p   7.4p  14.1p  14.1p   8.5p   5.7p   0.5p   0.2p
```

- **cat/global**: 중간 구간(2~10일)만 나쁘고 21일 이후 회복됨(콜드스타트 상품 특성 -
  초반엔 신규 협력사 프로세스가 안 잡혀 편차가 크지만 결국 다 도착).
- **vendor_mid**: 정반대 패턴 - 짧은 구간(1~14일)은 양호한데 21일(11.6%p)/30일(10.7%p)에
  "재검토 필요" 수준으로 나빠짐. 이건 처음 제안("sku/vendor_mid/vendor_cat/vendor는
  전부 high confidence로 묶자")에서 완전히 놓칠 뻔한 부분 - 검증 없이 진행했으면
  vendor_mid의 장기 확률이 실제로는 못 미더운데 "신뢰 가능"으로 표시될 뻔했음.

### 수정
단일 `reliable_from_day` 값으로는 이 반대 패턴(중간이 나쁜 것 vs 끝이 나쁜 것)을 동시에
표현할 수 없어서, `serve.py`에 레벨별 "불안정 day 집합"을 상수로 관리:
```python
LEVEL_UNRELIABLE_DAYS = {
    "sku": set(), "vendor_mid": {21, 30}, "vendor_cat": set(),
    "vendor": set(), "cat": {2, 3, 5, 7, 10}, "global": {5, 7},
}
```
(기준: 오차 >10%p = 이 프로젝트가 이미 쓰는 "재검토 필요" 기준과 동일하게 맞춤)

`predict()` 출력에 `confidence_level`(레벨 요약, high/medium/low)과 `by_day[].reliable`
/`headline.reliable`(구체적 day별 판정)을 추가. **모델/서버는 판단 근거만 제공하고,
화면에서 숨길지/흐리게 표시할지/문구로 대체할지는 UI 정책**이라 serve.py 자체 로직
(headline 계산, by_day 값)은 건드리지 않음 - `API_SPEC.md` 2번/5-2번 항목에도 반영.

### 남은 참고사항
- 45/60/90일 확장 지점(by_day, EXTRA_DAY_MARKS)은 레벨×day마크 캘리브레이션 검증 대상이
  아님(30일까지만 검증됨) - cat/global이 21~30일에 이미 회복되는 추세라 그 이후도
  안정적일 것으로 보고 기본 `reliable=True`로 두었으나, 실측 검증은 아님.
- **(2026-07-10 해결)** vendor_mid의 21/30일 불안정 구간은 이후 선택적 2022년 데이터
  확장으로 해소됨 - 위 "vendor_mid 21/30일 개선" 항목(파일 상단) 참고. 이 섹션의 표/코드는
  당시 발견 기록으로 그대로 두되, 지금 `LEVEL_UNRELIABLE_DAYS["vendor_mid"]`는 `set()`임.
- 재학습(`03_distribution_fit.py`) 주기마다 `LEVEL_UNRELIABLE_DAYS`도 같이 재검증해서
  갱신할 것 - 물량이 쌓이면 cat/global의 콜드스타트 문제 자체가 줄어들 수 있음.

## headline이 일요일 날짜로 표시되던 문제 (serve.py, 2026-07-07 수정)

### 원인
GUI에서 상품코드 10013100(종이컵)을 2026-07-07(화) 기준으로 조회했더니 headline이
"7/12(일) 도착 확률 90.9% (5일 후)"로 나옴 - 사용자가 "일요일엔 배송이 안 가는데 왜
일요일로 예측하냐"고 지적. 실측 확인 결과:
- 전체 배송완료일자의 요일 분포: 월 10.5%, 화 17.4%, 수 20.7%, 목 21.0%, 금 20.2%,
  **토 9.8%, 일 0.43%** - 일요일은 사실상 배송이 없는 날(토요일은 정상적인 배송일).
- 그런데 종이컵의 fd_4(토, 4일째)=82.0% -> fd_5(일, 5일째)=90.9%로 8.9%p나 뛰었음.
  이유: fd_d는 **모든 주문요일을 섞어서** 평균 낸 값이라(주문요일별로 세그먼트를 나누지
  않음 - 03_distribution_fit.py 상단 docstring에 이미 기록된 "주문요일 세그먼트 추가
  시도 후 되돌림" 결정과 같은 뿌리), 화요일에 주문해서 5일째가 일요일에 걸리는 경우에도
  "다른 요일에 주문했다면 5일째가 평일이었을" 케이스들의 실제 증가분까지 함께 평균에
  섞여 들어가 부풀려짐. 즉 90.9%라는 숫자 자체는 (전체 평균으로는) 맞지만, "일요일에
  도착한다"는 의미로 이 숫자를 그 날짜에 붙이는 건 틀림.

### 수정
`serve.py`의 `_headline()`에서 threshold를 넘는 날의 달력 날짜가 **일요일이면 건너뛰고
다음 날(항상 월요일 - CDF가 단조증가라 이미 threshold를 넘은 상태이므로 무조건 넘음)의
실제 fd 값을 채택**하도록 변경. 토요일(9.8%)은 정상 배송일이라 건너뛰지 않음.
- 종이컵 사례: "5일 후(일, 90.9%)" -> "**6일 후(월, 94.5%)**"로 변경 (요청대로 날짜와
  확률이 함께 바뀜 - 토요일로 내리면 82.0%라 애초에 90% 기준을 못 넘기게 되므로
  월요일로 올리는 쪽을 선택함).
- `build_analysis_workbook.py`의 `headline_of()`는 "N일 후"라는 상대 경과일만 표시하고
  특정 주문일자/달력 요일과 연결짓지 않으므로(세그먼트_상세/상품코드_조회예시 시트 -
  임의의 주문일에 대해 통용되는 일반 참고표) 이 문제와 무관 - 수정 안 함.

### 남은 참고사항
- **by_day 표(DAY_MARKS: 1,2,3,5,7,10,14,21,30)는 이 보정을 적용하지 않음** - 고정된
  경과일수 기준으로 캘리브레이션 검증(phase1_report.txt)이 이미 이 지점들로 이뤄져 있어
  임의로 날짜를 밀면 그 검증과 어긋나게 됨. 그래서 by_day는 "일요일이어도 그 경과일의
  실측 누적확률을 투명하게 보여주는 참고 표"로 그대로 두고, "여기가 확신할 수 있는
  날짜다"라고 못박아 말하는 headline에서만 이 보정을 적용함. by_day에도 같은 보정이
  필요하다고 판단되면 재검토할 것.
- **근본 원인(주문요일별로 세그먼트를 안 나눔)은 해결 안 됨** - 이번 수정은 headline
  표시 시점의 후처리(일요일이면 다음날로 넘기기)일 뿐, fd_d 값 자체가 여전히 모든
  주문요일을 섞어서 계산됨. 03_distribution_fit.py에서 이미 주문요일을 세그먼트 축으로
  추가하는 시도를 했다가 협력사/카테고리 축과 결합 시 캘리브레이션이 악화돼 되돌린 바
  있음(원인 미규명) - 근본적으로 고치려면 그 문제부터 다시 풀어야 함.

`YYYYMMDD`(날짜만)이고 시:분 정보를 담은 컬럼이 하나도 없음. 즉 현재 확보한 데이터로는
"마감시간 이전/이후 주문 구분"(예: 네이버의 "15:00까지 결제 시 오늘 발송") 같은 피처를
**절대 만들 수 없음** - 없는 데이터를 만들어낼 방법이 없다.

### 실무 영향
오전 주문과 밤 11시 주문을 모델이 동일하게 취급함. 마감시간에 가까운 주문일수록 실제로는
다음날 처리로 넘어갈 가능성이 큰데 이 효과가 반영 안 됨 - day1 확률의 정확도에 미세한
잡음으로 작용할 수 있음(정량화 안 됨).

### GUI 마감시간 가정 (2026-07-07 추가)
gui_predict.py에 CUTOFF_HOUR=15 도입: 주문일자가 오늘(기본값)이고 조회 시각이 15시
이후면 주문일을 다음날로 간주해서 계산하고, 헤드라인에 "[15시 마감 경과 - 내일(N/N)
주문 접수 기준]"을 명시한다. **확률 모델 자체는 안 건드림** - 시:분 데이터가 없어서
마감 효과를 검증할 수 없으므로, 검증 불가능한 확률 보정 대신 "주문일 해석"이라는
투명한 가정으로만 처리(다른 날짜를 직접 입력한 시뮬레이션 조회에는 미적용). 15시는
네이버 패턴을 참고한 임의 가정값 - 실제 마감시간 확인되면 상수만 바꾸면 됨.

### 트리거 (아래 발생 시 재검토)
- 박형근 차장님(통합플랫폼) 팀에 "실제 주문 시스템 DB/로그에는 주문 시각까지 기록되는지"
  확인 - 있으면 이 raw data 추출에는 빠졌을 뿐이니 추가 요청해서 마감시간 피처 검증 가능.
  없으면 이 오차는 구조적으로 감수해야 함(API_SPEC.md 3번 항목에도 기록됨).
- 실제 주문 처리 마감시간 확인 시 gui_predict.py의 CUTOFF_HOUR 갱신.

## 유가증권(상품권/기프티쇼) - 분석에 남겨도 되는지 확인 (2026-07-07)

### 확인 완료
사용자가 "상품권/기프티쇼는 배송이라는 개념 자체가 없는데 분석 의미가 있나" 질문 ->
데이터로 확인한 결과 **문제없음, 그대로 둬도 됨**:
- 진짜 기프티쇼/전자상품권 SKU(예: 스타벅스/이마트/CU 모바일상품권, 27개 확인)는 전부
  median 1일, 7일 이내 도착률 93~100%로 모델이 이미 정확하게 "즉시성"을 반영하고 있고,
  Kraljic 분류에서도 전부 레버리지재/일반재(저위험)로만 나옴 - 리스크로 잘못 잡히는 사례 없음.
- **주의할 점**: `대분류="출판/인쇄/여행/상품권"`이라는 이름이 오해를 부름 - 이 대분류는
  진짜 상품권(중분류="유가증권")뿐 아니라 명함/안전표지판/젠틀몬스터·탬버린즈 브랜드 포장재
  같은 **실제 인쇄물·제작가공품**(중분류="출판/인쇄", "제작가공품")도 섞여 있음. 이 대분류에서
  Kraljic 전략재/병목재로 잡히는 항목들은 전부 이 실제 인쇄물 쪽이지 상품권이 아니었음
  (예: "명함" median 4일, "안전표지판" median 7일 - 이건 진짜 인쇄/배송 리드타임).
  **대분류 이름만 보고 "이 카테고리는 다 상품권"이라고 오해하지 말 것.**

### 진짜 유가증권을 깔끔하게 걸러내려면
원본 데이터에 이미 깨끗한 구분 컬럼이 있음 - 카테고리명으로 유추하지 말고 이걸 쓸 것:
- `상품타입` = "유가증권" (2026년 기준 4,557건)
- `상품유형` ∈ {"GIFTI SHOW", "상품권", "모바일상품권"}
현재 `data_loader.py`의 USECOLS에 이미 포함돼 있는 컬럼들이라 추가 작업 없이 바로 필터 가능.

### 활용 (필요 시)
- 통합플랫폼 쪽에서 "즉시발급 상품은 도착확률 위젯 자체를 안 보여줄지" UX 판단이 필요하면,
  위 `상품타입`/`상품유형` 플래그로 걸러서 결정할 것 (카테고리명 기준으로 거르면 명함 같은
  실제 인쇄물까지 잘못 걸러짐).
- 모델/Kraljic 분석 자체는 수정 불필요 - 이미 상품코드 단위라 정확히 처리되고 있음.

## product_lookup.csv가 train(2023~2025)만 써서 2026년 신상품이 무조건 "전체 평균"으로 조회되던 문제 (2026-07-07 수정)

### 원인
`gui_predict.py`로 상품코드 10673012(외장HDD, 협력사 (주)중앙미디어테크)를 조회했더니
"전체 평균(신규/미등록 상품)"으로만 나와서 확인함. 실제로는:
- 이 상품 자체는 2026년에 신규 등록돼 2건 실주문(배송완료 1건, 7일 소요)이 있었음.
- 협력사 (주)중앙미디어테크는 2023~2025년에도 활발히 거래한 기존 협력사(SKU 1,241개
  보유, vendor 레벨 분포도 존재)라서 원래는 "협력사 평균"까지는 정확히 폴백됐어야 함.
- 그런데 `03_distribution_fit.py`의 `prod_map`(→`product_lookup.csv`)이 `train`
  (2023~2025)에서만 만들어지고 있어서, 2026년에만 등장한 상품코드는 상품명/협력사명/
  대분류/중분류를 아예 못 찾음 -> `serve.py`의 폴백 체인(상품코드->협력사x중분류->...)이
  전부 건너뛰어지고 곧장 global로 떨어짐. 확률분포(`tables`)는 정직한 홀드아웃 검증을
  위해 여전히 train만 써야 하지만, `product_lookup.csv`는 이름/협력사/카테고리
  매핑표일 뿐 확률 계산에 관여하지 않으므로 굳이 train만 쓸 이유가 없었음.

### 수정
`03_distribution_fit.py`에서 `prod_map`을 `train` 대신 `pd.concat([train, holdout])`
(2023~2026 전체)로 생성하도록 변경. 확률분포(`tables`)와 캘리브레이션 검증
(`evaluate_holdout`)은 그대로 train/holdout 분리 유지 - 이 부분은 건드리지 않았으므로
기존 캘리브레이션 결과에는 영향 없음.
- `product_lookup.csv`: 상품코드 수 대폭 증가 (2026년 신상품 포함), 135,315 SKUs로 저장.
- 재검증: 상품코드 10673012가 `level=vendor`로 정상 폴백, "(주)중앙미디어테크" 평균
  (n=10,514, median 3.0일)으로 예측되는 것 확인.
- 연쇄 재실행 필요: `product_lookup.csv`를 참조하는 `10_kraljic_delivery_risk.py`
  (category_vendor_count 계산에 사용)와 `build_analysis_workbook.py`도 재실행해서
  `kraljic_delivery_risk.csv`(2,171 rows로 갱신)와 `배송예측_분석보고서.xlsx`를 동기화함.
  04~09번 스크립트는 product_lookup을 안 쓰므로 재실행 불필요.

### 남은 참고사항
- **매년 재실행 필요**: 시간이 지날수록 train 구간(2023~2025)이 계속 과거로 고정되므로,
  매년 초 등 정기적으로 `03_distribution_fit.py`를 재실행해서 `product_lookup.csv`가
  최신 연도 신상품까지 포함하도록 갱신할 것 (holdout 연도 자체를 언제 늘릴지는 별개
  판단 - 그건 확률분포 재학습 주기의 문제이고, 이번 수정은 매핑표만의 문제).
- `배송예측_협의용_통합플랫폼.xlsx`(박형근 차장 공유용 발췌본)는 `build_meeting_excerpt.py`로
  마스터를 복사해서 만드는 구조라, 공유 전에 반드시 재실행해서 최신 세그먼트_상세를
  반영해야 함(아직 재실행 안 함 - 필요 시 요청).
