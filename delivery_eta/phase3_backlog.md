# Phase 3 백로그 (기회/우선순위 - known_risks.md와 별도로 관리)

known_risks.md는 "검증된 기능의 미확인 리스크"를 다루고, 이 파일은 "아직 손 안 댄
기회/확장 아이디어"를 다룬다.

## 담당자 쇼티지 경고 플래그 - 파일구조/연동 로직 완료, GUI 노출은 미팅 후 확정 (2026-07-09)

### 배경
사용자가 LTE-MUX 필터(상품코드 10013417/10013419, 협력사 (주)쏠리드) 수입 쇼티지로 인한
배송지연 사례를 제시하며 반영 방법을 질문. 확인해보니 이 두 상품은 이미
`kraljic_delivery_risk.csv`에서 **병목재**(공급위험 高, median 28일, lt_cv 0.57, 7일
도달률 10%)로 분류돼 있었음 - 다만 Kraljic 분류는 `10_kraljic_delivery_risk.py`/보고서용
워크북에서만 쓰이고 `serve.py`(실제 예측 엔진)에는 연결돼 있지 않았음.

### 검토한 세 가지 방법과 결론
1. **ECOS(거시경제지표)** - 기각. 향수/영풍기획 배치성 발주 건(위 항목)과 같은 이유 -
   환율/물가지수 같은 거시지표로는 특정 부품/벤더 단위의 개별 수입 차질을 설명 못 함.
2. **뉴스 기사 자동 모니터링** - 지금은 보류. NLP 매핑/실시간 파이프라인 구축 부담 +
   부품 단위 쇼티지는 애초에 기사화 안 되는 경우가 많아 커버리지가 낮음. 필요성이
   커지면 재검토.
3. **담당자 수동 입력(쇼티지 플래그)** - 채택. 구매담당자가 협력사로부터 이미 직접
   전달받는 정보(수입 지연 예상)를 상품코드 단위로 기록해두는 가장 가벼운 방식.

### 설계 원칙 - 확률 재계산 없이 경고만
담당자가 "지연 배수"나 "심각도" 같은 임의 숫자를 입력해서 확률분포 자체를 조정하는
방식은 채택하지 않음 - 검증 안 된 값으로 곡선을 왜곡하게 되어 이 프로젝트가 계속
지켜온 "임의 보정 지양, 실측 검증 후 적용" 원칙(공휴일 보정 방식과 동일 철학)에 어긋남.
대신 **기존 확률분포는 그대로 두고 경고 플래그만 얹는 방식**으로 설계.

### 현재 구현 상태 (2026-07-09, 사용자 확인: "예방적 아이디어" + "최소 구현(C안)")
- `shortage_flags.csv` 신규 - 컬럼: 상품코드/시작일/종료일/사유/입력자/입력일. 현재
  헤더만 있고 실제 등록된 플래그는 없음(예방적 설계 단계, LTE-MUX 실사례 미등록).
- `serve.py`: `DeliveryPredictor.__init__`에서 로드(파일 없어도 정상 동작, 빈 DataFrame
  폴백), `_active_shortage()`로 order_date가 등록 기간에 걸리는지 확인, `predict()` 반환
  값에 `shortage_alert`(bool)/`shortage_reason`(str|None) 추가. 검증 완료: 플래그가 없을
  때 기존 by_day 확률과 100% 동일(왜곡 없음), 플래그 기간 내에서만 alert=True.
- **미확정(보류)**: GUI(`gui_predict.py`) 경고 문구 표시 여부/방식, `API_SPEC.md`에
  `shortage_alert`/`shortage_reason` 필드 정식 반영 - 통합플랫폼이 별도 알림 체계를
  이미 가지고 있을 수 있어 박형근 차장 미팅에서 협의 후 결정. 지금은 API 스펙 문서를
  건드리지 않음(미팅 전 협의 문서 확장 자제).

## 배치성 발주 상품 - 재고연동 우선순위 후보 (2026-07-06, 2026-07-08 "수입" 표현 정정)

### 용어 정정 (2026-07-08)
처음엔 이 패턴을 "배치성 수입"이라고 불렀으나, 실제로 "수입"임을 확인한 적이 없다는
지적을 받고 재검토했다. 원본 데이터(109개 컬럼)에 원산지/수입여부 필드가 없고
(제조사 컬럼만 있는데 이것만으로는 국내/수입 판별 불가), "수입"이라는 원인 해석은
아래 관찰된 패턴(발주→출하가 유독 길고 특정 달에만 몰림)에 대한 **그럴듯한 추측이었지
검증된 사실이 아니었다**. 그래서:
- **검증된 사실**(그대로 사용): 발주→출하 구간이 유독 길다, 특정 달에만 주문이 몰린다 ->
  "배치성 발주 패턴"이라고 부른다.
- **미검증 추정**(원인 후보일 뿐): 해외 수입/통관 지연, 국내 정기 대량발주, 계절 상품
  비축, 프로젝트성 조달 등 - 어느 쪽인지 현재 데이터로는 확정할 수 없다.
- 재고연동(Phase 3) 우선순위 판단 목적이면 원인이 무엇이든 이 패턴 자체로 충분히
  유효하다. 통관/소싱 전략처럼 원인이 실제로 중요한 의사결정이 필요하면, 데이터로
  추론하지 말고 구매팀/MD에 원산지 마스터 데이터를 요청할 것.

### 발견 배경
`headline`(90% 도달일) 필드가 "미달"로 나온 상품코드 10534198(향수, 협력사 영풍기획)을
조사한 결과:
- 전체 median 27일 중 **발주→출하 구간이 25일**을 차지(출하→배송완료는 1일로 정상)
- 같은 달 안에서는 편차가 작음(표준편차 0.5~2.6일)인데 월별 median은 5~31일로 크게 다름
- 특정 달(11월/2월/7월 등)에만 주문이 몰림 -> **협력사가 정기적으로 배치(묶음) 발주해서
  재고를 채우는 패턴**으로 판단(원인은 미확정 - 위 "용어 정정" 참고). 배송이 느린 게
  아니라 "다음 입고분을 기다리는 대기시간"이 27일의 정체.
- ECOS(환율/물가지수 등 거시지표) 검토했으나 기각 - 이건 협력사 내부 재고/입고 스케줄
  문제라 거시경제 지표로는 알 수 없음. 오히려 김정훈 본부장 메일의 "알파 재고연동"과
  같은 종류의 문제(재고 있음/없음, 다음 입고 시점을 아는 게 핵심).

### 중요한 한계 (반드시 인지할 것)
**영풍기획(향수 사례의 실제 협력사)은 이 협력사 단위 스크리닝에 안 걸림.** 이유: 영풍기획은
향수 같은 배치성 발주 상품도 팔지만 동시에 청결용품(월 매출 규모 훨씬 큰 CS전용 상품, 전체
26,144건 중 대부분)도 꾸준히 팔아서, **협력사 전체로 집계하면 배치 신호가 희석됨**
(영풍기획 전체 집계: p90=26일로 기준은 넘지만, 월커버리지가 높아서(거의 매달 주문) 두 번째
조건에서 탈락). 즉 이 배치 패턴은 **협력사 단위가 아니라 상품(SKU) 단위 현상**이고,
지금 스크리닝은 "이 상품만 파는" 소규모 협력사만 잡아낸다. 영풍기획처럼 여러 상품을
섞어 파는 협력사의 특정 SKU 배치패턴을 잡으려면 `협력사x상품코드` 또는 최소
`협력사x중분류` 단위로 재실행해야 함 - 아직 안 함(비용 대비 실익 판단 필요, SKU 조합이
많아 연산량이 커짐).

### 활용 방안 (Phase 3 진입 시)
- 위 6개 협력사 + 영풍기획 같은 "혼합 포트폴리오" 협력사의 배치성 SKU를 재고연동
  (임영빈 팀장 알파 인터페이스류) 우선 대상으로 검토
- `headline` "미달" 상품에 대해 통합플랫폼에서 "다음 입고 예정" 같은 별도 안내 문구 검토
  (API_SPEC.md 협의 필요 사항에 추가 여지)
- 재실행 시 09_batch_import_vendor_check.py를 협력사x상품코드 단위로 확장

## 후속: 정식 Kraljic 리스크 분류로 대체 (2026-07-06, 완료)

위 09_batch_import_vendor_check.py의 임시 기준(협력사 단위, p90+월커버리지)을
`10_kraljic_delivery_risk.py`로 대체. `demand_forecast.py`에 만든 `classify_kraljic()`과
같은 철학(공급리스크 × 구매영향력 4분류)을 상품코드 단위(협력사 단위보다 세밀)로 적용해서
영풍기획 같은 혼합 포트폴리오 협력사의 배치성 SKU까지 정확히 잡아냄 - 09번 스크립트의
한계를 실제로 해결.

**공급 리스크 판정 기준(2개 이상 충족 시 高)**:
- 발주→출하 CV(변동성) > 0.3
- 중분류 내 협력사 2곳 이하 (시장에 대체 공급사가 실질적으로 없음)
- 7일 이내 도착률(OFR 개념, segment_distributions.csv의 sku 레벨 p_7d 재사용) < 85%

**시행착오 기록**: 처음엔 "벤더의존도"를 product_lookup.csv의 `n_협력사_고유값==1`
(상품코드 자체가 단일 협력사인지)로 시도했으나, 전체 상품코드의 97%가 원래 단일 협력사라
구분력이 전혀 없었음(대부분 高리스크로 오분류, 88.6%). **"대체 가능성"은 상품코드가
아니라 중분류(카테고리) 단위로 봐야 한다** - 같은 종류 상품을 파는 협력사가 시장에 몇 곳
있는지가 실제 리스크 지표. 교체 후 분포가 훨씬 합리적으로 나옴(전략재 11.2%, 병목재
14.0%, 레버리지재 37.7%, 일반재 37.2%).

**구매 영향력**: 매입금액 데이터가 없어 ABC(파레토, 금액 기준) 대신 주문량(n) 파레토 사용
- 배송예측 맥락에선 "몇 명의 고객 경험에 영향을 주는지"가 금액보다 직접적인 지표라는 판단.

**결과**: `kraljic_delivery_risk.csv`(2,171개 상품코드 전체), `kraljic_delivery_risk_report.txt`
(전략재/병목재 상위 20개 상세). 영풍기획의 다른 상품(렌즈클리너/구강청결제/탈취제 등
"[CS물품 전용]" 계열, 7일도달률 0.1~17%)도 향수와 같은 배치성 패턴으로 재확인됨 -
초기 발견(향수 1건)이 이 협력사의 특정 카테고리 전체에 일반화되는 패턴임을 확인.

09_batch_import_vendor_check.py는 참고용으로 남겨두되(협력사 단위 개요가 필요할 때는
여전히 빠르게 참고 가능), 정식 우선순위 판단은 10번 스크립트 결과를 사용할 것.

## 코드 상수의 근거 소실 감사 (2026-07-07)

### 발견 배경
`serve.py`의 `LEVEL_UNRELIABLE_DAYS`를 만들 때, 그 근거(레벨×day마크 전 구간 캘리브레이션
오차표)가 대화 중 일회성 계산으로만 나왔고 어떤 리포트 파일에도 저장이 안 되어 있었음 -
즉 "왜 이 상수가 이 값인지"를 코드만 보고는 재현할 수 없는 상태였다. `03_distribution_fit.py`의
`evaluate_holdout()`에 이 표를 계산해서 `phase1_report.txt`에 정식 저장하고,
`build_analysis_workbook.py`가 파싱해서 캘리브레이션_검증 시트에 반영하는 것으로 해결
(known_risks.md의 "레벨별 불안정 구간" 항목 참고).

### 활용 방안 (Phase 3 진입 시 또는 여유 있을 때)
같은 문제(코드 상수의 근거가 리포트 파일에 없고 대화/기억에만 있음)가 다른 상수에도
있는지 감사해볼 것. 확인 후보:
- `serve.py`의 `PRE_HOLIDAY_WINDOW = 3` - 08_holiday_adjustment.py의 검증 결과와
  정확히 일치하는지 (아마 있음, 확인만 필요)
- `03_distribution_fit.py`의 `MIN_N = 1000`, `SKU_MIN_N = 200` - 04_recency_diagnosis.py의
  "30건→1000건으로 올려서 문제 해결" 기록과 연결되는지 (known_risks.md에 이미 기록돼
  있어서 우선순위는 낮음)
- `05_growth_vendor_flag.py`의 급성장 배율(5배), 최소물량(500건) 기준
- `10_kraljic_delivery_risk.py`의 `LT_CV_THRESHOLD=0.3`, `OFR_THRESHOLD=0.85`,
  `MAX_CATEGORY_VENDORS=2` - phase3_backlog.md(이 파일) 위쪽 섹션에 근거는 있으나
  리포트 파일 자체에는 없음

각 상수마다 "이 값의 근거가 되는 계산이 재실행 가능한 리포트 파일에 남아있는가"를
확인하고, 없으면 이번처럼 스크립트에 계산을 추가해서 저장할 것.

## cat/global 콜드스타트 개선 - 데이터 확장 필요 (2026-07-08)

홀드아웃 4.7%(cat+global)의 캘리브레이션 오차가 큰 문제를 배송형태 축으로 세분화해서
풀어보려 했으나 실패(cat/global 내부의 99%가 이미 "협력사배송" 하나로 쏠려있어 구분력
없음) - 상세 원인/시도 내역은 known_risks.md의 "cat/global 콜드스타트 세분화 시도"
항목 참고. 현재 데이터(주문 이력)만으로는 더 이상 세분화할 축이 없고, 신규 협력사
온보딩 정보(업종/규모/소재지/사전 SLA)처럼 **주문 이력이 아닌 별도 데이터**가 있어야
개선 가능 - Phase 3에서 구매팀/MD, 통합플랫폼팀과 이런 데이터 확보 가능성을 협의할 것.

### 후속: 배송지(지역) 축 - counterfactual 검증 결과 기각 (2026-07-08)
처음엔 cat/global 내부를 배송지 첫 토큰(시/도)으로 나눠보니 지역별 7일 도달률이 최대
20~30%p 차이가 나서(대구/전남 40%대 vs 경남/강원 70%대) 유망해 보였다. 하지만 이건
서로 다른 지역의 **단순 그룹 평균 비교**였을 뿐이고, vendor_cat 제거 때 썼던 것과 같은
"같은 주문에 두 방식을 동시 적용"하는 counterfactual 검증을 거친 뒤 결론이 뒤집혔다:

```
(같은 주문 기준, MIN_N=1000)
cat x 지역    vs cat 단독:    day3/7/10 전부 지역이 근소 우위지만 개선폭 0.3~0.4%p뿐(미미)
global x 지역 vs global 단독: day3/7/10 전부 global 단독이 우위 - 지역 추가하면 오히려 악화
  (day3 7.4%p->7.7%p, day7 14.1%p->14.9%p, day10 8.5%p->9.4%p)
```

**결론: 반영하지 않음.** 처음 본 20~30%p 지역 차이는 "그 지역에 어떤 카테고리/협력사
주문이 몰렸는지"의 차이였지 지역 자체의 효과가 아니었다(cat 레벨처럼 카테고리를 이미
통제하면 차이가 거의 사라지고, global처럼 통제가 없으면 지역 정보가 오히려 노이즈로
작용해 악화됨) - vendor_cat 사례와 정확히 같은 유형의 착시. **"진짜 구분력이 있어
보인다"는 이전 평가는 틀렸다** - 그룹 평균 비교만으로 세분화 여부를 판단하면 안 된다는
원칙이 다시 한번 확인됨. 더 세분화할 다른 후보가 나오지 않는 한 이 방향은 재시도하지
않을 것.

## 여름/연말 품목별 계절 수요 검토 (2026-07-08, 계절가전 검증 완료 - 기각)
사용자 질문("여름 장마/태풍 수해, 더위로 인한 수요 급등, 연말 예산 소진 주문 몰림")에서
"연말 예산 소진"과 겹치는 **전사적 캘린더 근접 효과**(하루짜리 공휴일 직전 물류 지연)는
확인·반영 완료(known_risks.md의 "하루짜리 공휴일 보정 누락" 항목 참고).

**"여름 수요 급등 → 배송 지연" 가설은 계절가전(에어컨/선풍기/온풍기/제습기/가습기/
공기청정기/전기장판)으로 검증 완료 - 기각.** 실제로 6월에 물량이 4배 가까이 급증하는
건 확인됐지만(1월 115건 -> 6월 431건), 캘리브레이션은 오히려 성수기(6월, day7 오차
2.9%p)가 비수기(2월, 19.0%p)보다 정확했음 - 정반대 결과. 원인은 train 데이터 자체가
이미 성수기 물량 비중이 커서 vendor 레벨 예측이 자연스럽게 성수기 패턴에 가깝게
형성되기 때문으로 추정. 상세 내용/수치는 known_risks.md의 "계절성(여름 수요 급증)
및 카테고리 체계 개편" 항목 참고.

**부수 발견**: 이 과정에서 대분류/중분류 카테고리 체계가 2025-12-29에 개편된 사실을
확인(사용자 확인 + `서비스 카테고리 담당자 관리회계.xlsx` 공유받음). "관리회계"
필드로 더 안정적인 cat 레벨을 만들어보는 것도 같은 방식(같은 주문 counterfactual)으로
검증했으나 기각 - 기존 대분류 방식이 더 정확함(관리회계가 너무 성기게 묶여서 오히려
악화). 이것도 known_risks.md 참고.
